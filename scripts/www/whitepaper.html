ETCS — Entity Tag Component System

A Unified Causal Substrate for Secure, Extensible, and Ontology-First Computing

Anticurrent Entropy Inc. · Pre-Release — 2026

Abstract

ETCS (Entity Tag Component System) is a C++ substrate in which type identity, ABI contract, capability boundary, and causal graph are one compile-time artifact rather than four that must be kept in agreement. A module declares its types and the actions they answer to; that declaration is simultaneously its export list, its ABI surface, its capability grant, and the set of operations a script can address. Built on CRTP-based static dispatch with a materially instantiated ontology tag stack, ETCS eliminates the traditional separation between design-time type hierarchies and runtime execution models. Access control is structural rather than enforced: a capability does not exist unless the corresponding header is present in a module’s compilation unit.

Because the .etcs causal-trace language is expressly not Turing-complete — no branches, no loops, no accumulating state — a trace contributes no state of its own beyond the entities it binds and the events it orders. A module’s reachable causal state is consequently bounded by concrete properties of the substrate rather than by assumption: an alphabet capped at 64 declared types by the width of the compile-time relation matrix, an ordering space bounded by that same constant, a canonical comparison relation under which instance recycling closes into a detected cycle, and a 300ms interruption contract that bounds per-transition cost and makes interior non-termination an observable admission failure. An exhaustion pipeline, now in development, traverses that space under two comparison relations — one distinguishing entity identities and one treating them as equal up to renaming — generates the trace set that constitutes a module’s certificate, and marks explicitly the regions where the graph does not close.

A module’s complete export horizon is legible at its binary boundary before load, which makes that certification reproducible by any party rather than attested by the operator alone. The artifact travels with the evidence for its own claim as a causal certificate: verification is open to any party holding the module and the public ontology, and a signature adds weight rather than validity. The certificate is exhaustive over causal shape and sampled over the single content channel the call interface presents; what it does and does not bound is stated precisely in Section 4.4 and its limits consolidated in Section 4.9.

The result is that security, extensibility, ABI stability, and deterministic replay are consequences of one architectural decision rather than independently maintained systems. The runtime is free, the ontology and core are LGPL, and Section 1 states what ships, what it costs, and what it does not yet do.

1. What This Replaces

1.1 The Artifacts You Currently Keep in Sync

A C++ project that loads third-party code maintains several systems that have nothing to do with what it does. A plugin loader and a version negotiation scheme. Symbol versioning to keep an ABI from breaking across a release. A sandbox policy, or the decision not to have one. A serialization layer and something to move it between processes. Signing infrastructure, if the code came from someone else. Tests that exist only to check that an interface still means what it meant last month.

None of these is the product. All of them drift, because they are separate artifacts describing the same relationships and nothing forces them to agree. A type is declared in one place, its ABI guaranteed in another, its permissions in a third, and its call graph nowhere at all.

ETCS makes them one artifact. The claim is not that each problem is solved better; it is that they stop being separate problems, because the type declaration, the ABI contract, the capability boundary, and the causal graph are the same compile-time object seen from different sides.

1.3 What Writing a Module Looks Like

A complete, working SQLite binding is about seventy lines. The type inherits one CRTP base, fills in four concrete slots, and declares which of its methods are addressable from a script:

class SqliteLocalDatabase : public LocalDatabaseBase<SqliteLocalDatabase> {
public:
    WIRE_TYPE_IDENTITY(SqliteLocalDatabase);
    void CreateConnectionConcrete(const ETCS::Buffer& db_info) override { /* ... */ }
    bool ExecuteRawConcrete(ETCS::Buffer& data) override { /* ... */ }
    // CloseConnectionConcrete, InitializeSchemaConcrete similarly.
};
ETCS_TAG_BLOCK_BASIC(SqliteLocalDatabase, Query, Execute, Close, Delete)

There is no dispatch logic to write, no identity registration beyond one macro, no lifecycle wiring, no serialization, and no ABI declaration. The base supplies all of it, and the tag block is simultaneously the export list, the ABI surface, the capability grant, and the set of actions a script can address — because in this substrate those are one thing.

Adding a second family costs one clause and its obligations. Swapping SQLite for Postgres is another one-line inheritance discharging the same four slots, and every script written against the constraint runs against it unmodified. Appendix A works this through the shipped ontology in full.

2. Architecture

2.1 The Ontology as Type System

The ETCS ontology is a directed acyclic hierarchy of types organized into lineages. Each lineage represents a conceptual domain: Database, Network, Renderer, InputDevice, and so forth. Within each lineage, types are progressively specialized: Database -> LocalDatabase -> SQLiteDatabase. A leaf type such as SQLiteDatabase is a concrete realization of its entire lineage.

Critically, this hierarchy does not exist only at design time and evaporate into a vtable at runtime. The full lineage is materially present on every leaf instance as an instantiated tag stack. The hierarchy is not scaffolding that produces a flat runtime structure. It is a permanent property of every instance.

Not every node in a family is directly claimable, and the rule is structural. A CRTP base — the proxy a concrete type inherits in order to prove it satisfies a constraint — sits at a leaf of the family tree. Interior nodes publish an interface and no base: they declare a constraint for their descendants to refine, and no provided type occupies them. Database is such an interior node. The leaves carrying bases are LocalDatabase and RemoteDatabase, and a provided type claims one of those rather than Database itself.

Placing a base on an interior node is possible and never necessary. Where a type appears to need an interior position, the answer is to add a more specific leaf beneath it and carry the base there — one declaration, and the rule stays uniform.

Two consequences follow. Only a node carrying a base contributes anything to a module’s export horizon, so only such a node has hash identity in the sense of Section 2.3. And the composition space Section 4.2 treats as closed is the product over the leaf sets of the family trees rather than over all their nodes, which is a smaller set and the correct one to count.

A vocabulary distinction runs through the rest of this document and is easiest to fix here. An ontology node is a position in one of these family trees — Database, LocalDatabase, Deletable, Ephemeral — authored as a trait interface and its CRTP base, maintained under LGPL, and shared by every module. A provided type is a concrete leaf a module declares in its tag block, claiming one node from each family it participates in and discharging the obligations those walks accumulate. SqliteLocalDatabase is a provided type; LocalDatabase is an ontology node. Both are loosely called types in ordinary use, and the difference between them is load-bearing in Sections 2.5 and 4.7.

The two are governed differently. The ontology is the monotone object: nodes are added and never contracted, because signed modules depend on the constraints they claim (Section 4.7). A module’s provided types are not part of that object at all. A developer may add, remove, rename, or restructure the types their module provides as freely as any other implementation decision, subject only to the capacity of Section 2.5, because a provided type is a claim against the ontology rather than a part of it.

2.1.1 Families as Trees; the Composition Lattice

Lineages are tree-shaped, and composition across them is governed by a small, closed algebra. Within one family, membership is cumulative: a leaf claiming a node in the tree assumes the union of obligations along the entire walk from that node back to the shared Entity root, which every family reaches virtually, collapsing all such walks into a single subobject. Across one family, siblings at a branch point are exclusive: two specializations of the same constraint cannot be held simultaneously, as a semantic matter of what an entity is. Across different families, composition is free and intended — a leaf draws one node from each family it participates in, and its full constraint surface is the union of the corresponding walks.

The space of legal shapes is therefore the product over the leaf sets of the family trees, closed before any module is written. A second kind of exclusivity can arise between families that were never designed relative to one another, purely through a coincidence of vocabulary; it does not remove compositions from that space but attaches a mandatory, compiler-forced disambiguation to particular ones, and it is described in Section 2.1.2.

The composition space remains finite and closed under both resolutions, and that closure is the first of the bounds on which Section 4.2’s argument rests.

2.1.2 Incidental Exclusivity

The exclusivity described above is structural: siblings under a shared parent are exclusive because they are two specializations of one constraint, and that is authored up front. A second kind arises by accident of vocabulary, and it is worth describing separately because it behaves differently in every respect.

Two families sharing no ancestor may each declare a dispatch method under the same name, for unrelated reasons — one family’s Close releasing a network connection, another’s finalizing a parsing session. The names coincide; the constraints do not. A provided type folding both families in still compiles, because the two outer methods are complete, non-virtual members sitting in separate base subobjects. The error arrives at the first unqualified reference to the shared name, where the compiler finds two unhidden candidates and declines to choose between them. This is ordinary C++ ambiguous member lookup rather than a mechanism peculiar to ETCS. What is deliberate is leaning on it as a discovery tool and removing the ways it could be evaded.

The dispatch macro removes them. Because the inner *Concrete requirement is token-pasted from the outer name at a single call site, there is no way to author an inner requirement without its paired dispatcher under the same stem, and no way for two differently-named methods to land on the same inner symbol. Under hand-written forwarding a quieter failure was possible: two families with different outer names could coincide on an identical inner name, and one leaf override would silently satisfy both unrelated slots — double duty with no diagnostic at all. The outer collision and the inner collision are now guaranteed to co-occur, so the immediately-diagnosed ambiguity is the only failure that can happen.

This exclusivity is pairwise rather than partition-wide: a family that collides with one other combines freely with every family it does not collide with. It is discovered lazily, at the first attempt to combine rather than at authorship. And it is escapable, by either of two routes. An explicit merge writes one combining function that calls each family’s implementation by qualified name under an authored policy — both must succeed, either suffices, run both in order — leaving each family’s inner slot distinctly named and uncontaminated. Composition by reference declines the inheritance entirely, holding the second family as a separate addressable entity reached through the ordinary call surface. The test between them is whether running both implementations back to back leaves the object consistent with each family’s invariants independently. Where satisfying one requires violating the other — one Reset assuming imminent destruction, the other assuming reuse — the two constraints did not belong on one entity, and reference is the correct answer.

Lazy discovery would be a hazard if the surface were not enumerable, and it is. Every name a family claims originates from exactly one dispatch-macro invocation, so a single scan across the ontology’s dispatch declarations identifies every family claiming a given name, exhaustively. Whether two families are combinable is therefore a tooling-level audit rather than a coincidence an author has to notice by reading two interface files side by side.

Two things should be kept apart here, because “not visible from one file” would otherwise fuse them. The ontology is a dictionary: the trait vocabulary, published under LGPL, legible in full to everyone, and the thing a collision scan resolves. No part of it is withheld, and no question about it requires loading anything. Which objects exist against that vocabulary is a separate matter with a separate answer. Provided types are module-owned and are held or not held; the dictionary describes what could be said, and holding a module is holding something that says it. The distribution controls of Sections 3.1 and 5.1 govern the second question — what a party has been given — and never the first, which is public by construction.

2.2 CRTP Proxy Leaves and Static Dispatch

Every leaf type in the ETCS ontology is a CRTP (Curiously Recurring Template Pattern) proxy. CRTP provides static polymorphism without virtual dispatch: the type relationship is resolved at compile time, and a base’s outer method reaches its leaf’s implementation by static cast to the derived type rather than through an indirection.

A vptr is nonetheless present on every leaf, because interface headers declare their obligations as pure virtuals over a virtually-inherited Entity root (Appendix A.1), and it is worth saying plainly why that is not a contradiction. The vtable exists so that the compiler enforces the structure — a leaf that fails to discharge an obligation does not compile — and it is never dispatched through, because the loader resolves concrete ontology types and every call site therefore knows what it is calling. The vtable is a compile-time obligation checker that happens to be materialized at runtime, not a dispatch mechanism. There are no dynamic casts and no type erasure.

A caller holding a Database tag invokes the concrete SQLiteDatabase implementation directly through the Database interface. The function being called is always the leaf’s implementation. The tag stack determines which subset of that implementation’s surface is nameable from a given vantage point, not which function executes.

The tag stack is not a vtable chain. It is a set of typed views onto a single function table, where the view determines what is nameable but not what executes.

2.3 Hash Identity and Type Ownership

Each type in the ETCS ontology carries a hash that serves as its identity, and that hash is derived from compiled code rather than assigned to the type by declaration. Every ETCS ABI function a type carries has its own hash mirror — the _GetHash accompanying each trampoline (Section 2.7) — which hashes the code segment of the function it corresponds to. A type’s identity is the Merkle sum of those function hashes, computed at compile time and fixed thereafter.

The derivation gives the identity a property an assigned identifier would not have: it is tamper-evident at the granularity of a single action. Because a function’s hash is a hash of that function’s own code, a work function whose code segment has been modified yields a hash that is not the one recorded for it, and the disagreement is internal to the artifact rather than requiring comparison against an external registry. This is a separate mechanism from the load-time header handshake of Section 3.2, which detects modification of the participating interface rather than of an implementation; the two are complementary and neither subsumes the other.

The hash is defined by the type provider module itself, not by an external registry or runtime type system. Two properties follow:

The hash for a given type is constant regardless of runtime instance — SQLiteDatabase always has the same hash. Two types that share an identical method surface are nonetheless distinct. LocalDatabase and RemoteDatabase refine the same shared constraint and declare no obligations beyond it, so a reader comparing their interfaces sees the same methods; their hashes differ because each carries its own CRTP base and therefore its own ABI functions, which are different functions with different code. Identity does not follow from method surface, and two nodes agreeing on every signature are not thereby the same node.

Identity is therefore absolute and module-owned. No two types are the same regardless of shared interface surface. The type provider is the sole authority on identity, and this authority is stable across DLL, shared object, WebAssembly, and process boundaries without requiring a shared runtime type system.

2.3.1 The Call Primitive: Entity, Data, and Context

Every causal operation in ETCS is a work function invocation carrying exactly three things. What each contributes bounds the arguments of Sections 3 and 4, and they are introduced here rather than assumed there.

The entity is the operand, addressed by its RID. A RID is a deterministic sequence value — an incrementing nonce combined with the type tag and hashed — so the same script run twice produces bit-identical RID sequences, and the n-th instance of a type always receives the same identity. What a RID designates is a causal position rather than a name: an entity’s continuity back to its origin, the property that stays identical under every change the trace makes to that entity’s state. Section 4.2 draws on this directly, since what a certificate must preserve is position-in-structure and not labelling.

The data is the only content channel. The system is otherwise stateless by design: a work function receives no ambient input, reads no shared mutable region, and consults no global registry, so everything that can vary between two invocations of the same action on the same entity arrives through this one argument. Its contents are interpreted strictly on the Turing-complete side — opaque to the causal grammar, which has no construct for reading a value at all.

The context is a SignalContext, and it sits in a tree with two edges. The passive edge runs to the enclosing scope — work function to module scope to root scope, where the root observes global signals such as an interrupt from the terminal — so that a signal raised at any level reaches everything beneath it. The active edge binds to the most local context, so that a specific work function can be targeted without disturbing its siblings. Both surface to the author through a single isInterrupted() check, and the contract is that no more than 300ms may elapse between checks.

The contract is cooperative in expectation and enforced in fact. Once a signal is raised, a module that has not observed it within the window is terminated by a watchdog, which tears down the runtime. That is severe by design and it is not a hazard: termination is an exit condition reached deterministically, and a module that provokes it reaches the same terminal state on every run that provokes it. An interior may therefore fail to terminate, and may sit in a blocking call where it executes no instruction of its own and can observe nothing — what it cannot do is leave the system without a bounded response. Section 4.2 draws a bound on traversal cost from exactly that.

Immediate and streaming actions

An action is either immediate or streaming, and which it is is declared per action at the export horizon, where it appears as a _Work or a _Stream trampoline (Section 2.7). The distinction is one of lifetime and contract, not of channel: both kinds carry their content in data.

An immediate action takes its content, does its work, and returns. A streaming action operates under the produce/consume contract, and its content is carried by a MirrorBuffer that serializes itself through the same data argument. A MirrorBuffer determines the gap between two locales and mirrors state across it, so that both sides can treat a type with remote residence as though it were locally held — provided each holds the modules supplying the wrappers needed to compose and decompose it. Those wrappers apply and peel in layers according to which side of the contract a participant occupies, which is how the transport generalizes the network stack rather than sitting on top of one. It is also why the capability to participate in a stream is the ordinary capability of Section 3.1 rather than a separate grant — though the barrier is not the trait vocabulary. The ontology is public (Section 2.1.2), and any party can name the constraints a wrapped type satisfies. What a party may lack is the specific provided types the wrap chain is built from, and without them it cannot reconstruct the chain locally however much of the vocabulary it can read. The buffer is then inert to it: legible as a shape, unopenable as a thing.

Because mirrored state travels as a serialization over data, the channel count does not change. A streaming action presents the same single content surface an immediate one does, differently structured. This holds for stream configuration as well as stream payload: a buffer’s configuration is a property of the MirrorBuffer, which serializes and transports itself across the boundary, so anything read from it is downstream of the data argument rather than arriving beside it. An action that appears to take its content from stream configuration rather than from data is reading the same channel one layer in. Variable-length payloads travel this way rather than entering the module arena as allocations (Sections 2.8, 4.2), which is what keeps unbounded shapes off the allocation stream.

The three arguments therefore partition cleanly: identity is canonical and structural, content is opaque and singular, and control is ambient and bounded. No fourth channel exists, which is the property Section 2.7 states from the other direction and the property Section 4.5 relies on when it samples content.

2.4 The LMAX Causal Buffer

Inter-module communication in ETCS is mediated by an LMAX-style ring buffer that enforces strict causal ordering across the runtime event graph. This buffer is not merely a performance optimization. It is the mechanism that makes the (entity, data, context) call primitive compose identically across thread, DLL, process, and network boundaries.

The causal ordering semantics of the buffer define a partial order over all inter-module events. An event cannot precede itself in this partial order; the relation is inexpressible in the primitive. What follows from this is a property of the event dependency graph, not of the module reference graph: no event can be causally blocked on its own completion, and by transitivity no set of events can be mutually blocked. The acyclicity the transport layer guarantees is therefore acyclicity of causal dependency among events — which is deadlock freedom by construction — and it is not a claim that modules may not refer to one another. They may, and ordinarily do; Section 2.6 separates the three graphs involved.

2.5 The Two Ordering Mechanisms and Their Duality

ETCS expresses causal ordering at two distinct scales, which are complementary and non-interfering.

Compile-time causal ordering is expressed through the GapReorderBuffer’s dependency matrix. Each type provider owns a local EventStream carrying a 64×64-bit relation matrix over the module’s declared types. Each bit position in that matrix is a declared type; each type carries a 64-bit row encoding its relations to every other type in the module, populated at compile time from the CRTP edges by which types reference one another — addTag<T>, spawn<T>, and the remainder of the typed-reference vocabulary. Every event carries a tag_closure_mask, a vector over that same index space, encoding which causal domains it touches. When a new event arrives, its mask is intersected against all in-flight events — if no intersection exists, the event passes through at full LMAX throughput. If an intersection exists, the event is held until its blocking predecessor drains.

The matrix width and the module’s type capacity are the same constant, and not by coincidence: a module may declare at most 64 provided types because a sixty-fifth would have no bit position to occupy and no row in which to record its relations. The complete intra-module type-relation graph is therefore a fixed 512-byte object, resolved at compile time, permanently L1-resident, and — as Section 4.2 uses it — a computable ceiling on what any trace addressed to the module can name.

Two further structures share that width without sharing that reason. The EventStream’s ring holds 64 in-flight slots, and the GapReorderBuffer’s blocked-by matrix is 64×64 bits over those slots, recording which in-flight event currently waits on which. That matrix is runtime state: it mutates as events arrive and drain, and it is distinct from the compile-time relation matrix above, which never changes after compilation and is indexed by type rather than by slot. The ring is 64 deep because 64 is a good depth for cache residency at this access pattern, not because there are 64 types. The alignment is convenient and the two constants are independent.

A third bound sits at the same value for a third reason. The macro machinery that expands a tag block admits at most 64 actions per type, so a type declares no more than 64 actions and a module therefore exports at most 64 × 64 = 4096 action trampolines. That ceiling is known before any binary is read, and Section 4.2 uses it. A module’s tag list is likewise bounded by what its declaration string can carry, which is the same 64-type limit expressed at the point of declaration rather than at the point of representation. Exceeding either limit is a compile-time failure rather than a runtime one, though the diagnostic surfaces inside macro expansion and is correspondingly unhelpful.

Runtime causal ordering is expressed through the produce/consume work function pairs that connect providers across module boundaries. These are explicit, typed declarations of cross-provider causal relationships. The consumer’s local EventStream sees cross-provider events arrive sequentially through the ring, providing natural serialization at every boundary. By the transitivity of the chain, global causal ordering is maintained without any global coordination mechanism.

The compile-time mechanism handles the closed world of a single provider’s type space. The runtime mechanism handles the open world of arbitrary cross-provider topology. The produce/consume pairing constraint is what keeps them from needing to know about each other.

The only event class that requires global coordination outside this duality is memory topology change — module creation and deletion. This is handled exclusively by the loader, which is the single authority for topology mutations. All other ordering requirements are fully covered by the two mechanisms above.

2.6 Cycle Containment and Deadlock Freedom

Three distinct graphs are commonly conflated when a system of this shape is described, and the guarantees differ across all three. Stating them separately is worth the paragraph.

The include graph is acyclic. This is a property of C++ compilation, not of anything ETCS contributes, and it is noted here only for completeness.

The module reference graph may contain cycles, and in practice usually does. A module A that sends to B and receives a response from B participates in a cycle in this graph. Request/response is the ordinary case, the produce/consume pairing of Section 2.5 is explicitly bidirectional, and ETCS neither prevents nor wishes to prevent this.

The event dependency graph is acyclic by construction, and this is the guarantee the transport actually supplies. Each module is a locally cyclic, isolated state machine owning its own compute, memory, and scheduling; internal cycles are unrestricted. All external interaction passes through the LMAX buffer, where an event’s position in the partial order is fixed at admission to the ring and where the relation blocked by therefore cannot close on itself. A cyclic wait is not disallowed by a check; it is not representable.

The resulting property is stronger and more useful than acyclicity of the module graph would be. Mutually referential modules are permitted, arbitrary internal state machines are permitted, and the system-level guarantee is that no configuration of them can deadlock through the causal primitive. High local dynamism is combined not with a restricted topology but with a restricted failure mode.

2.7 The Export Horizon

Every causal operation a module exposes is an exported symbol. Each type declared in a module’s tag block contributes a uniform export set: a Make, MakeChild, List, and GetHash quartet for lifecycle and identity, and a _Work or _Stream trampoline per declared action, each paired with its own _GetHash. Which of the two an action carries is not incidental: it declares, statically and in the symbol table, whether the action is immediate or operates under the produce/consume streaming contract (Section 2.3.1). MakeChild is the entry point behind the producer minting discussed in Section 4.2.

Alongside these the module carries a small fixed set of its own — Cleanup, GetArena, which exposes the module-scope arena that backs every allocation beneath it (Section 4.2), and a module-level GetHash — together with the two hooks through which the loader installs itself, RegisterDynamicLoader and RegisterRootSignalContext. That is the complete export set, and it is the set the module’s linker script admits. There is no other channel: a caller cannot reach behavior that is not exported, and nothing is exported that was not declared.

That set is the module’s export horizon, and everything Sections 3 and 4 operate on is some property of it. Which types a module provides, which actions each type carries, and whether each is immediate or streaming are readable from the compiled binary’s dynamic symbol table alone, with standard tooling, before the module is ever loaded. Identity requires one step further into the same binary rather than a step outside it: because a type’s hash is the Merkle sum of hashes over its ABI functions’ code segments (Section 2.3), the values are computable by any party able to read those segments, which is any party holding the artifact. Nothing about identity depends on loading the module, on calling its accessors, or on consulting a registry the operator controls. The horizon is a boundary in the literal sense: identity is fully legible from outside it, and behind it the implementation is opaque and irrelevant to what can be expressed against the module.

The horizon is total by construction, not by discipline. In the ETCS execution model there are no ambient side channels for a caller to reach: I/O is an action on a provider entity, concurrency is a detached trace whose every line is again an action, and memory is arena-owned per entity and mutated only through the same event machinery, with topology change serialized by the loader as the single authority (Section 2.5). To cause an effect and to invoke an exported trampoline are the same act. Everything Sections 3 and 4 describe — structural access control, causal exhaustion, signing — operates on this horizon and nothing else.

2.8 The Constraint Surface, the Horizon, and the Interior

A type in ETCS carries two independently authored surfaces, and everything behind both is a third thing.

The constraint surface is what a type must satisfy to legitimately claim its identity: the accumulated dispatch-method obligations inherited by walking each of its ontology families back to the shared Entity root (Section 2.1). This surface is the authorship contract — it is what the CRTP base templates enforce at compile time, and it is what the type’s hash identity is bound to.

The export horizon (Section 2.7) is what the module actually exports: the actions declared in its tag blocks, one trampoline each. This is what .etcs traces address and what exhaustion traverses (Section 4).

The two are deliberately not required to coincide. A module may export helper actions that are not part of any family’s contract, and may satisfy contract obligations it chooses not to export as script-addressable actions, invoking them internally instead. The gap between them is developer workspace: the constraint surface fixes what a type is, the horizon fixes what can be said to it, and an author decides how much of the former to expose through the latter. Exposing a constraint obligation directly as an exported action — a one-line work function forwarding to the concrete implementation — is the recommended path where the two are meant to align, but it is a convention, not a requirement of the substrate.

The division is an allocation boundary as well as a naming one. Fixed shapes — the declared types, and the structs the interior uses — are allocated from the module arena. Variable-length content is not allocated there at all: it is carried by the produce/consume pair as a MirrorBuffer with a structured lifetime, which is what keeps unbounded shapes off the allocation path (Sections 4.2, A.6).

Everything behind both is the interior: ordinary, Turing-complete C++, unconstrained in implementation, unreachable by name from any trace. The interior is where the exhaustion claim of Section 4.2 draws its line — it is precisely the part of a module that exhaustion does not, and need not, enumerate.

2.9 Performance Characteristics

The ordering machinery of Sections 2.4 and 2.5 is where throughput is decided, so its measured behavior belongs beside it.

2.9.1 LMAX Primitive Throughput

The underlying LMAX ring buffer sustains approximately 200 million operations per second under benchmark conditions with an L1-resident ring (~64KB, optimal for low producer counts) and approximately 2.5 million operations per second under the sequenced ordering path. The autotuner identifies two distinct regimes and selects ring geometry accordingly: small L1-resident rings for low producer counts where cache residence dominates, and large rings (32–64MB) for high-contention workloads where throughput is the constraint.

2.9.2 The GapReorderBuffer: Zero Cost in the Common Case

The GapReorderBuffer is architecturally significant not only for its correctness guarantees but for its throughput characteristics in realistic workloads. The dependency matrix is sparse by construction. The vast majority of events within a single provider’s EventStream are causally independent — they touch disjoint tag_closure_masks and have no blocking relationship. In this common case, the acquire() call scans 64 slots of hot L1 data (the blocked-by matrix over ring slots is 512 bytes, always cache-resident; Section 2.5), produces a zero blocked_by entry, and drain_ready() immediately emits. The slot cycles Empty → Pending → Running → Complete → Committed → Empty without ever materializing a stall. Throughput in this case approaches the LMAX primitive ceiling.

When a dependency is present, the stall is local. Only the specific slots whose tag_closure_masks intersect are held. All other slots in the GAP_DEPTH window continue draining at full speed around the blocked event. There is no global barrier, no pipeline stall affecting independent work — the ordering cost is paid only at the exact causal intersection point and nowhere else.

A third case — the already-resolved dependency — costs nothing at all. If the event that would have been a blocking predecessor has already drained before the dependent event arrives, the new event sees an empty matrix and passes through at full LMAX speed. The ordering guarantee is preserved; the cost is never paid.

The GapReorderBuffer provides ordering guarantees that are free until needed, local when needed, and never paid for work that is already done. Amortized over realistic workloads, throughput approaches the LMAX primitive ceiling with causal ordering as a structural property rather than a performance liability.

2.9.3 The Ordering Duality as a Performance Property

The separation between compile-time ordering (bitmask matrix, provider-local) and runtime ordering (produce/consume pairs, cross-provider) is not only a correctness and isolation property — it is a performance property. Cross-provider ordering never enters the bitmask machinery. The GRB matrix remains sparse because it only tracks intra-provider dependencies, which are the minority of all dependencies in a well-factored module graph. The runtime ordering mechanism (the LMAX ring between providers) handles cross-provider sequencing at the transport layer with no coordination overhead in the GRB.

3. Structural Access Control

3.1 Capability as Header Inclusion

The most architecturally significant property of ETCS is that capability and dependency are the same concept. A module can interact only with types whose headers are present in its compilation unit. If a header is absent, the type does not exist in that compilation unit — the reference simply does not exist.

This is not access control in the conventional sense. Conventional access control is a positive claim: this principal has permission X. The attack surface is the permission-granting mechanism. ETCS access control is a negative space: a module can only operate on what it has explicitly declared a dependency on. There is no permission to forge, no token to steal, no escalation path that does not require modifying the build itself.

The build graph is the coupling graph. The compilation graph is the security graph. The dependency graph is the authority graph. These are not parallel artifacts. They are the same artifact.

The scope of this guarantee is narrower than it may read. Header inclusion bounds the ontological reach of a module: which types it can name, which causal relationships it can express, which actions it can address. It does not constrain the interior implementation of a work function the module legitimately provides — that interior is ordinary C++ with ordinary process capability, and its scrutiny belongs to a different mechanism operating at a different point in the lifecycle: the certification pipeline of Section 4 and the distribution authority of Section 5, before the module ever reaches a user, together with the sandbox observation performed during exhaustion. Structural access control answers “what can this module express against the ontology”; admission authority answers “should this module’s implementation be trusted at all.” The two guarantees are complementary and should not be read as one.

One further scope note belongs here, because the mechanism is easily credited with more resolution than it has. Capability granularity is the granularity of the ontology, not a property of header inclusion itself. Holding a database constraint’s header may confer the ability to execute arbitrary statements against a connected store; holding a page type’s header may confer arbitrary reads beneath a mount point. Neither is a defect in the mechanism — a module still cannot name what it was not given, and cannot decompose a transport whose wrapper types it cannot name (Section 2.3.1) — but the unit being granted is whatever the ontology chose to make a node, and a coarse node grants coarsely. Since ontology nodes are the permanent object (Section 4.7), where a family is cut is a decision with permanent consequences for how finely capability can be apportioned. Cutting them at a useful granularity is therefore a design obligation on the ontology’s authors rather than something the substrate supplies.

3.2 Compile-Time Enforcement

This pushes access control to the earliest possible point in the software lifecycle — not runtime, not link time, not type checking, but the preprocessor. Before a single type is resolved, the vocabulary of what a module can express is fixed by its include graph.

The security implication is significant. A third-party module author can interact only with types whose headers were distributed to them. The set of types accessible to a module is determined at the moment the SDK is handed over, not at the moment the module executes. The trust boundary is header distribution.

The compile-time trust boundary described above is enforced at load time by a bilateral handshake. Participating header hashes are embedded in both the loader and every module. At static-initialization time, the module reaches into the loader as the loader reaches into the module, and each side independently affirms or rejects the connection based on hash alignment and a set of further structural integrity checks on its counterpart. Rejection by either side refuses the load.

Because affirmation is mutual, the handshake cannot be satisfied by modifying one side to accept the other’s altered state: a valid pair is an equilibrium that a legitimate build produces jointly, and a unilateral hand-patch — including editing a loader’s embedded hash table, which itself perturbs the binary in ways the module side checks — does not reproduce it. The bond between a distributed runtime and the modules it loads is therefore tamper-evident at every load, today, independent of the certification pipeline described in Section 4.

The one thing this handshake structurally cannot address is an adversary who reproduces an entire independent build rather than modifying an existing artifact — but such an adversary has not forged the trusted system; they have built a different one against the open interface, which is the case Section 3.4 takes up next.

3.3 Ontological Absence vs. Filtering

A module that does not hold a given tag does not see the corresponding type as restricted. It does not see it at all. Inaccessible content is ontologically absent rather than filtered. This distinction has security consequences: there is no filter to bypass, no audit gap between should not access and cannot access.

3.4 The Loader as the Locus of Guarantee, Not the Open Interface

Because CORE is openly published and sufficient on its own to specify what a loader must honor (Section 1.5), any technically competent party can write an independent loader against it — not by forking Anticurrent Entropy Inc.’s own loader source, which is not released, but by building fresh against the same open interface. The bar for “is technically a loader” is low: a bare entry point and the CORE headers are enough to begin instantiating entities and running modules against the shared ontology, however far short such a thing would fall of the hardened, hash-verifying, sandbox-interposing binary this document describes.

Such a loader is not a security hole. It is a different, unguaranteed system that happens to share an open interface: it can load ETCS-conformant modules, which are unchanged, but it carries none of the structural-access-control, hash-attestation, or causal-certification properties above, because those belong to the specific key-bearing runtime Anticurrent Entropy Inc. distributes rather than to the interface any loader must satisfy. It sits outside this trust graph in the same way any independently written software does.

This is the defensibility argument of Section 5.8 one layer down: the asset was never the code, open or otherwise.

4. Causal Exhaustion and Module Certification

4.1 The Two Scripting Layers

One division in the language precedes the exhaustion argument, because it determines what the pipeline generates, what a developer writes, and which of the two a certificate is made of.

Import-level scripts are what a module’s causal exhaustion generates against its export horizon — machine-produced, one per distinct causal shape the module admits. Collectively they are its trace set, and the trace set is the certificate (Section 4.4). Export-level scripts are developer-authored composition over those pieces, and are the layer at which the data channel (Section 2.3.1) is populated. CORE specifies the grammar both layers are written in; only the import layer is generated, and only the export layer is authored.

Script inclusion belongs to the grammar and divides along the same line. An export script may run or detach another script, which is how composition over generated primitives is expressed at all. A generated import script does not: it addresses a module’s exported actions directly and includes nothing, which is what keeps a certificate independent of what happens to be resolvable on disk when it is checked (Section 4.4). The distinction is worth holding because the interactive shell accepts commands beyond the grammar — listing, job control, exit — which are conveniences of that tool and not part of what CORE specifies or what non-Turing-completeness is a property of.

Grammar and horizon divide the vocabulary between them. The .etcs grammar contributes structure — context, roles, spawn, the produce/consume pairing, detachment, signaling — together with the bounding conditions Section 4.2 establishes. Each module’s export horizon contributes the operational half, which types and actions a trace can address, and ships it in the binary.

The division decides where decidability lives. A loader implementing a different driver language over the same exported symbols — one with branches, loops, or accumulating state — would run conforming modules and forfeit the bounded-state property entirely, because a driver that accumulates state contributes state no bound on the module side can recover. Decidability is a property of the specified grammar rather than of the ABI, and it travels with CORE rather than with any runtime.

4.2 The Source of Decidability: Bounded Causal State, Not Bounded Program Text

Causal exhaustion is possible because of what is exhausted, not because of how much compute is thrown at exhausting it. A type-providing module is written in ordinary C++: Turing-complete, capable of arbitrary internal logic, unconstrained in how a developer implements the behavior behind a given tag’s actions. Exhaustion does not attempt to enumerate the reachable states of that C++ implementation, which would be undecidable in general.

It is equally important to say what exhaustion is not enumerating on the other side. It is not the set of expressible .etcs scripts. That set is countably infinite: scripts of unbounded length over a finite action alphabet are unboundedly many, and non-Turing-completeness does not change this. Non-Turing-completeness gives decidability of an individual trace — every trace terminates, and its effect is computable — which is a different property from finiteness of the trace set, and the two should not be run together.

What is enumerated is the reachable causal state, and it is a projection of a module’s total state rather than the whole of it. Naming the projection precisely matters, because every result below is a result about the projection.

The projection comprises three things: the configuration of live entities and their tag sets; the binding environment mapping a trace’s role names onto those entities; and the in-flight ordering state among events addressed to them. The binding environment belongs in the definition because binding overwrites unconditionally — a rebound name points at a different entity, and identical subsequent trace text then addresses different things. It is bounded and readable, since a trace’s name set is lexical and finite.

What the projection excludes matters equally. Interior state that gates surface behavior is not in it: a connection flag that decides whether an action does anything, a transaction flag that decides whether a commit succeeds. Neither are effects a module produces outside causal state, such as rows written to a backing store. Two configurations identical under the projection may therefore correspond to module states that differ.

This scopes everything that follows. Traces are the means of reaching states, not the object being enumerated; a certified trace set covers the projected state graph, and its size is governed by that graph rather than by script length. Closure detected during traversal is closure of the projection: a cycle report states that the enumerated causal configuration returned to one already visited, and does not state that the module did. That is a weaker claim than closure of the module, it is the claim the certificate makes, and Section 4.9 records what follows from the gap.

The grammar’s restrictions are what make this reduction legitimate. Because .etcs has no branches, no loops, and no mutable variables in the conventional sense — role names are named slots binding entity instances, not variables accumulating computed state — a trace contributes no state of its own. Beyond the actions a trace addresses, the grammar’s own vocabulary (context selection, role binding, spawning, detachment, signaling, and script inclusion, together with each type’s lifecycle and introspection entry points) is orchestration defined by CORE rather than causal action on module state. Two executions arriving at the same entity-and-ordering configuration are therefore at the same state regardless of the length or shape of the path taken. In a language with accumulating state this collapse would be invalid and the enumeration would necessarily be over paths, which is the unbounded object above.

Five properties of the substrate carry the argument. Each is a concrete constant, a structural mechanism, or a computed per-module result — none is an assumption about modules in general.

4.2.1 The addressable alphabet is capped at a compile-time constant

A module declares at most 64 types, for the representational reason given in Section 2.5: each type occupies one bit position in the module’s relation matrix, and there is no sixty-fifth position. Each declared type contributes a fixed export set to the horizon — a Make/MakeChild/List/GetHash quartet and one trampoline per declared action (Section 2.7) — and a type declares at most 64 actions, for the same macro-expansion reason given in Section 2.5. The alphabet a trace can address against a module is therefore bounded above by 4096 action trampolines, and that ceiling holds before any particular binary is read. Reading the symbol table replaces the ceiling with the module’s actual figure, which is ordinarily far smaller.

The relation matrix bounds more than the alphabet. Because every typed reference between types in a module sets a bit at compile time, the complete intra-module type-reference graph is a compile-time artifact rather than something discovered by running the module. What types can reach what other types is known before exhaustion begins, and is 512 bytes. Section 4.5 uses this a second time, as the declared half of a coverage differential.

4.2.2 Ordering state is bounded by the same constant

The ordering component of causal state is the set of in-flight tag_closure_mask intersections, and a mask is a vector over the same 64-position index space. The ordering state a module can occupy is therefore a bounded bitfield by construction, its width fixed by the same fact that fixes the type cap.

4.2.3 The causal view and the identity view

RIDs are deterministic (Section 2.3.1), so determinism of identity is not in question. What requires stating is which of two comparison relations the certificate is taken over, because the reachable state graph has a different shape under each.

Under the identity view, two states are the same only if their entities carry the same RIDs. Under the causal view, two states are the same if they are the same up to consistent renaming of entity identities — the relation ordinarily called alpha-equivalence, and computed by replacing each RID with its ordinal of first appearance within the trace before hashing.

The causal view is the correct one for certification, and the reason is a property of the language rather than a modeling preference. A .etcs script cannot read a RID. It has no branches, so it cannot condition on one; no arithmetic and no equality test, so it cannot compare two; and no accumulating state, so it cannot retain one. A RID appearing in a trace is a binding, not a value. This is visible directly in how scripts are written: a script accepts an entity passed into it or instantiates one itself, and behaves identically either way, because what it requires of a role is that the slot be the correct shape — the right tag composition, the right action surface — and never that it be a particular occupant.

This is what it means for a RID to be a causal position rather than a name (Section 2.3.1). A certificate must preserve position-in-structure, which the causal view does exactly, and need not preserve labelling, which no program in the language can observe. Two traces differing only by a consistent renaming are one trace under two labellings, and a hash that separated them would be discriminating on a difference the substrate does not expose.

Both renderings are retained and both are reported, because the difference between them is itself informative. Where the causal view closes and the identity view does not, the divergence is exactly the signature of instance recycling, and it is a memory and performance finding rather than a certification failure. Where both diverge, the finding is a genuine non-closure and is handled as described below and in Section 4.6.

Canonicalization is a property of the comparison, not of the runtime. Entities carry their real RIDs throughout execution, and the store-and-rehydrate path of a persistent tag resolves against those, not against a per-trace ordinal.

4.2.4 Population closes by cycle, and closure is detected rather than assumed

Because the grammar has no loops and no branches, the number of entities a trace spawns directly is a property of the trace text: a script containing twelve spawn statements spawns twelve entities, on every run, in the same order. Script-driven population is not a dynamic quantity requiring a bound; it is a lexical constant readable from the script.

Production is the case where population is not fixed before execution. A producer work function’s interior is ordinary C++ and may mint children without static limit under external drive. Three facts about the substrate determine what that does to the state graph.

Causal state is a configuration of live entities; a freed child is not in it. Whether arena occupancy tracks that configuration depends on the allocation path, and the property is structural rather than incidental.

Sub-arenas do not allocate. Every entity carries its own arena and is expected to allocate from it, but that arena forwards its requests up the parent chain to the module arena, which is the sole real allocator for a type provider. Allocation shapes therefore pool across the whole provider rather than fragmenting per scope, and freeing follows the same chain in reverse.

Where an allocation is anchored is a discipline the substrate does not enforce and the certificate does report. Memory taken at module scope rather than against an entity persists until the module unloads, and module unload is gated on every entity in the module’s root scope having been released — so a module-scope allocation behaves as a leak for the whole life of the module, and shows up as a causal path that does not close (Sections 4.6, 5.4). Anchoring allocations to the entity they belong to is what makes population and occupancy track each other. Those shapes are fixed at compile time: the declared types, capped at 64, together with whatever structs the interior allocates — which are also defined shapes, and are commonly shared across several types within a provider, so one class serves many allocation sites and recurs more often than any single type would produce.

Variable-length data does not enter this path at all. It is carried by the produce/consume pair as a MirrorBuffer under a structured lifetime contract between two locales (Sections 2.8, A.6), which is what keeps unbounded shapes off the allocation stream and leaves the arena seeing only recurring classes.

A released child therefore leaves a hole shaped exactly like the next child, and the next mint reoccupies it. The arena’s high-water mark is the concurrent live population rather than the cumulative mint count. And under the causal view, a mint following a free returns the projection to a configuration already visited: same tag composition, same relation rows, same live count, renamed occupant.

A producer that mints and frees indefinitely therefore does not walk an unbounded path through the state graph. It walks a cycle in a bounded one, and covering a cycle is something a traversal does natively. The exhaustion tooling detects closure and marks it: a region that closes is reported as a cycle, and a region that does not is reported as an infinity, explicitly and per module. Whether a given module’s producer behavior closes is consequently a computed result carried on the certificate, not a property assumed of modules generally. The concurrent-live-population high-water mark observed during traversal is reported alongside it.

What remains genuinely open is monotonic minting: a producer that allocates without releasing, where live population climbs, neither view closes, and the sequence terminates only at arena exhaustion — which halts the system deterministically rather than diverging silently. This is a reported finding requiring justification at submission (Sections 4.6, 5.4), not a failure of the enumeration, and there are legitimate designs that exhibit it.

4.2.5 The interruption contract bounds cost

The SignalContext every work function receives carries a deadline: no more than 300ms may elapse between calls to isInterrupted(), which surfaces both edges of the signal tree described in Section 2.3.1. The interior remains Turing-complete and may fail to terminate. What it may not do is leave the system without a bounded response, because the deadline is backed by a watchdog that tears down the runtime when the window passes unobserved.

That is what bounds traversal cost, and it is the answer to the objection that a decidable procedure need not be a tractable one. The traversal is never hostage to a transition of unbounded duration: it raises a signal and regains control within a known window, either because the module observed it or because the watchdog fired. Cost is governed by the traversal’s own decisions and by the graph’s size rather than by an open question about the modules being traversed. Interior non-termination is not an unbounded hazard but a bounded, observable, admission-time failure, and an interior cannot conceal behavior by declining to return.

The scope should be stated precisely, since this is narrower than a per-transition time limit. What is bounded is the interval in which control can be reclaimed, not the duration of an uninterrupted transition — a module executing a long operation against which no signal has been raised runs for as long as it runs. And code parked in a blocking descriptor call executes none of the module’s own instructions and can observe no flag at all: the cooperative path does not reach it, and the watchdog is the only mechanism that does. It applies by termination rather than by cooperation, which is a coarse instrument and a deterministic one.

Elapsed time is a continuous quantity, and this check is the one point at which the substrate deliberately couples one to a discrete causal event. The coupling is safe in the direction that matters: the causal event is the author’s call to isInterrupted() returning true, not the elapsed interval itself, so the transition is grammar-expressible and exhaustible in the ordinary way. Timing determines when the flag is observed, never whether an interrupt is a causal event. A module whose checking cadence sits close enough to the boundary that the observation point moves between runs produces exactly the trace non-equivalence failure of Section 4.6 and fails admission. Adequate timing margin is a certification condition rather than a matter of author discipline.

4.2.6 The shape of the traversal

The traversal does not branch freely per mutation. Its unit is two levels and recurs.

An arbitrary root is a work function call, and what it first resolves is a single question: did anything happen. A call that mutates nothing terminates there. Where something does happen, the first degree of freedom is determined and the structure branches, and each branch resolves into settled states — each of which carries a reference back to the same root position it descended from, which is the continuity described above under the causal view. The unit is therefore a two-level expansion terminating in leaves that re-present their own root, and traversal proceeds by recurring that unit rather than by accumulating depth per mutation.

This is the same shape the composition lattice exhibits in Section 2.1.1, where a family walk composes with a free product across families and terminates at two levels because the second level is a product rather than further recursion. The expectation, stated as an expectation rather than a measurement, is that traversal growth is therefore governed by the same closed algebra that governs composition, and remains bounded at full type capacity rather than growing as a free product of choices along a path. Section 4.9 records what has and has not been established about this.

Decidability against tractability

Traversal is exhaustive over the graph these properties bound, rather than a sampling approximation of it. What is sampled instead of exhausted is the content of the data channel, and Section 4.5 states that scope directly.

The precedent worth naming is eBPF is the working industrial example of a deliberately restricted, verifier-checked in-kernel language, and it is the closest prior art to the argument made here. It is also a decade-long demonstration that a decidable verification target is not thereby a cheap one: eBPF’s verifier has contended with state explosion on programs well inside its stated bounds, and has been the subject of a steady stream of soundness CVEs in its own right. ETCS’s response to the first half of that lesson is the type cap, the interruption contract, and the recurring traversal unit, which together make cost a function of a bounded structure rather than of author behavior. It has no response to the second half beyond the ordinary one: the verifier is trusted code, and Section 4.9 says so.

Type-providing modules are Turing-complete and developer-authored. The causal traces run against them are not. Decidability is a property of the .etcs grammar under the conditions above, not a claim about the modules it addresses.

4.3 The Admission Operator

Module admission in ETCS is governed by an operator C that maps a module and the current ontology state to either an updated ontology state or rejection:

C : (Ui,ΔOi) → Ui + 1 ∪ ⊥

If coherence fails, no state transition occurs. If coherence succeeds, the ontology is atomically updated. There is no partial integration, no staged adoption, no coexistence of incompatible ontology versions. The system maintains a single active induced causal closure at all times.

4.4 What Causal Exhaustion Means

Causal exhaustion is the procedure by which C evaluates a candidate module. It is not testing, and it is not verification against an external specification. It is the traversal of the reachable causal state graph described in Section 4.2 and the generation of the trace set covering it.

Generation rather than checking is what determines the shape of a submission: the developer supplies the artifact and the pipeline supplies the traces, which is why what arrives is a module rather than a test suite.

The trace set

Exhaustion emits the import layer of Section 4.1: every import script expressible against a module’s export horizon, exhaustive over the state graph of Section 4.2. That set is hashed, and the hash serves as the causal identity of the module:

TM = {τ1, τ2, …, τn}

The hash is taken over the canonical form described in Section 4.2 — each entity identity replaced by its ordinal of first appearance — so that two runs differing only in nonce sequence produce identical certificates, as the language’s own inability to distinguish them requires.

What the certificate asserts, precisely

A certificate covers a (module, target) pair rather than a module. A module’s tag blocks and typedefs are compiled under preprocessor conditions, so its export horizon is target-dependent by construction: a provider may expose one leaf under Linux, another under WebAssembly, and nothing at all on a target it does not yet support. Exhaustion enumerates the surface that the compiled artifact actually presents, which is the surface for the target it was built against. A module intended to ship on several targets passes exhaustion on each, and carries a certificate for each; the transparency log records the target alongside the module hash (Section 5.8.2).

Within that scope, the certificate states that the module’s export horizon is exactly the enumerated one, that the causal-state transitions observed during traversal were exactly those recorded, that the regions of the graph which close and those which do not are exactly as marked, and that a second traversal under the same conditions reproduces all of it. Because generated import scripts include no other scripts (Section 4.1), reproduction does not depend on what is resolvable on the checking party’s disk; the certificate is a function of the artifact and the ontology, not of a search path. It is a statement about causal shape. Its scope should not be read past that.

The horizon already gives a reader the alphabet (Section 2.7). What exhaustion adds is the dynamics: which transitions actually fire, in what causal order, under which preconditions, with what closure structure, and at what resource cost — none of it present in a symbol table. The addition is real and it is bounded, because the interior behind each transition is Turing-complete, arena-owned, and mutable; Section 4.5 states which conditions the pipeline varies against it.

Scoping to causal state

The determinism guarantee is over causal state — an entity’s identity, its tag and type set, and, where a tag’s data is persistent, the store and rehydrate path defined by whichever persistence-handling traits that tag’s type declares, itself part of what exhaustion exercises rather than a persistence blind spot.

Entity identity is included in that comparison rather than excluded from it, in canonical form. What is excluded is the machine address an instance happens to occupy, which is an allocation artifact carrying no causal content. The distinction matters: ETCS does not exclude identity because identity is unreliable — RIDs are fully deterministic — it compares identity up to renaming because renaming is invisible to the language, and it excludes only the address.

A wall-clock reading, an address, or any other continuous quantity is not part of the trace two exhaustion runs are compared against and is not required to match between them. The grammar has no construct for conditioning on a continuous value directly; only a discrete tag transition is a causal event the grammar can express, execute, or exhaust. The single deliberate coupling between a continuous quantity and a discrete transition is the interruption check of Section 4.2, whose scoping is given there.

The ordering of tag transitions that do occur is guaranteed by the relation matrix (Section 2.5): two runs may differ in exactly when a transition occurs, but never in what transitioned or in what causal order, because that order is fixed by compile-time type relations rather than by timing.

What the scoping does not cover

The grammar’s inability to condition on a value bounds what a trace can say. It does not bound what an interior can do. The implementation behind a work function may read the clock, the environment, or the content of the data it was passed, and reach a different addTag as a result. The resulting tag transition is discrete, grammar-expressible, and well-formed — and if the condition did not hold during traversal, the transition did not occur and the certified set does not contain it.

What is structurally self-enforcing is therefore narrower than it may first appear, and the narrow version is the one this document claims: divergence observed across the pipeline’s stages is a pre-admission failure rather than a runtime hazard (Section 4.6), and cannot be tolerated as a quiet mismatch afterward. Divergence conditioned on something no stage varies is not observed. Section 4.5 states which conditions are varied, and describes the coverage differential by which an unexercised capability is nonetheless visible.

The causal certificate, and what a signature adds

A signed module travels with the evidence for its own claim. The trace set is carried with the artifact, and the signature states that this enumeration was produced by exhaustion of that artifact — which is what this document means by a causal certificate, and the sense in which a consumer establishes the claim by checking rather than by trusting whoever produced it.

The term is chosen in preference to proof-carrying code, which names something adjacent and stronger. Proof-carrying code ships a machine-checkable proof that a stated safety predicate holds, discharged by a proof checker. A causal certificate proves no predicate and invokes no checker: it reports what a module’s reachable causal behavior is, and it is checked by re-running the traversal that produced it. Section 7 draws the comparison out. The two make different promises, and only one of them is made here.

The trace set is a proof object rather than a test report in the specific sense that it is recomputable by a third party. Causal exhaustion is doable by any party holding a module and its declared ontology, using nothing beyond the language’s own decidability under the conditions of Section 4.2 — and holding the module is holding the operational half of that ontology, since its export horizon is carried in the binary and legible before load. The structural half is the CORE-specified grammar (Section 1.5) together with the ontology’s composition rules. All of it is public; none of it is the operator’s private state. What a consumer can in principle recompute is the certificate itself, with the scope stated above, rather than an attestation resting on trust in whoever produced it.

This separates two things that are usually fused, and the separation is the point. The proof needs no authority. Any party holding the module and the public ontology can run the traversal, obtain the same trace set, and sign that result; nothing about the procedure is the operator’s to grant. Signatures are nonetheless ranked. A signature is a claim of the form I ran this and obtained this, and what it is worth depends on who is making it — on their competence with the ontology, the care of their execution, and how exposed they are if the claim turns out to be wrong. A signature from the party that maintains CORE and ONTOLOGY weighs more than one from an arbitrary third party, not because the operator’s arithmetic is privileged, but because the maintainer is the party with the deepest working knowledge of the thing being verified and the most to lose from a bad certificate.

Both hold at once, and neither weakens the other. Verification is open, which is what makes the certificate a proof rather than an assertion. Trust in any particular signature is reputational and therefore unequal, which is what makes the operator’s signature worth acquiring. A domain that rejects the operator’s authority entirely can still verify every artifact it receives and sign its own results — the guarantees do not travel with that signature (Section 3.4), but the checkability does, which is what makes cross-domain legibility possible at all.

No enumeration tooling exists yet, at Anticurrent Entropy Inc. or anywhere else (Section 8). Anticurrent Entropy Inc. intends to be the first operator to build and run this tooling at production scale, not the only party architecturally capable of doing so.

4.5 Verification Stages

Certification runs in three stages against the properties of Section 4.2. None is deployed: the build server, the sandbox, and the enumeration tooling are target infrastructure, with status in Section 8.

Stage one: exhaustion and generation

Run on every submission. Causal exhaustion in a hypervisor-monitored sandbox traverses the reachable causal state graph, generates the covering import-script set, marks closed and non-closing regions, and hashes the canonical result. Its output is either certification of that set or the specific invalid traces the module produced, returned to the developer as executable diagnostics (Section 5.8.1). This is the stage a developer interacts with iteratively.

Stage two: data fuzzing, on submission

The first stage is a loop a developer runs as often as they like. The second is triggered by an act: pressing submit, which is the developer’s own declaration that the sandbox report is good enough to take to market. A passing report is a precondition for that act and is not itself the act — holding one does not put a module in front of a reviewer.

Submission opens a one-day grace period during which the fuzzing campaign runs, and no reviewer sees the module before it completes. What reaches review is therefore the post-fuzz picture rather than the report the developer chose to submit on. Beyond that grace period a reviewer will respond within two weeks; a submission still on the backlog at that point is reviewed by the operator directly.

Placing the campaign here rather than in the iterative loop keeps its cost proportional to modules whose authors have committed to selling them rather than to submission volume. It also means the developer, not the pipeline, chooses the confidence level at which their judgment gets tested — they iterate until they are willing to stake a submission, and the campaign tests that judgment before a reviewer spends attention on it.

The data argument is the only content channel into the causal layer (Section 2.3.1), and that singularity is what makes fuzzing worth doing here rather than merely conventional. Fuzzing is ordinarily weak evidence because it samples one channel among an unknown number, and the residual risk is dominated by the channels not fuzzed. The export horizon closes that gap: data is provably the only content channel, so the sample is taken over a known and singular space.

Streaming actions do not add a second surface to cover. A MirrorBuffer serializes itself through the same argument, so a campaign against data exercises the mirrored wire format as a matter of course — truncated, malformed, and adversarially structured buffers are targets on the surface already being fuzzed rather than a separate effort against a separate channel. Two properties of the pipeline sharpen it further. The build server compiles the module, so fuzzing is coverage-guided against real edge feedback rather than blind mutation. And the ontology declares the expected shape of data per action, so campaigns are structure-aware — seeded from the declared buffer schemas rather than spending their budget on parse rejection.

A fuzz hit does not merely flag a defect. Where a data value opens a causal path the initial traversal did not reach, the path is returned as an export script, and the certified set is extended to include it. The stage is a coverage mechanism whose output is more certificate.

Determinism under fuzzing is an admission criterion, and stating it precisely requires keeping the work function separate from what sits behind it. A work function is a point on the export horizon: the exported action a trace addresses, and where causal state is deposited. The implementation behind it is ordinary C++, free to compute however it likes. What the criterion tests is the surface, not the implementation — a given data value must produce the same causal-state transitions through that action on every run. Two runs may take different paths through the interior and still pass, provided the causal state they deposit is identical; that is the same scoping Section 4.4 applies to the certificate as a whole. Defensive handling of the argument is therefore a condition of certification rather than a matter of style, because an implementation that mishandles a malformed value and deposits differently has failed at the surface regardless of what it did internally.

The criterion is narrower than it may sound. It establishes that the causal state deposited through an action is reproducible for a given input. It does not establish that the action deposits the same state across inputs, and an interior branch taken only on one specific value is perfectly reproducible on every value that is not that one. Fuzzing reaches such a branch only where the guiding coverage signal leads to it. This is why the coverage differential below exists, and why it does not depend on the fuzzer landing a hit.

Stage three: air-gapped reproduction

Run once per module, late. After a submission has exhausted cleanly, survived the fuzzing campaign, passed review, and concluded price negotiation (Section 5.4), and before marketplace release, an air-gapped build server independently reproduces the traversal and compares canonical hashes.

The air-gapped condition is the point of the stage. A module whose causal structure reproduces identically while networked and diverges when the network is absent has revealed that some part of its behavior is conditional on reachability. In the benign case this is an undeclared environmental dependency; in the case the stage is positioned against, it is behavior deliberately held dormant while observable.

The sequencing is what makes this economically sound. Reaching this stage requires an author to have passed exhaustion, staked a submission, survived fuzzing, opened a negotiation thread bound for publication, and agreed a list price — sustained, identifiable effort under operator observation, all of it spent before the one test specifically designed to catch what such an effort would be concealing. The operator pays for the expensive reproduction only after the counterparty has committed that effort. The cost asymmetry runs against the adversary, and it does so because the stage is late rather than despite it.

The coverage differential

Every typed reference between types in a module sets a bit in the compile-time relation matrix (Section 2.5), including references that occur inside branches which never execute. A capability a module reaches for is therefore declared statically whether or not it is ever exercised. addTag<T> inside a branch gated on an unguessable value still sets its bit.

This makes a differential computable rather than requiring the trigger to be found: the declared transition set minus the transition set observed during traversal.

The declared side has two halves, both static and both readable before the module runs. Intra-module reach is the relation matrix, which records every typed reference among the module’s own provided types. Cross-module reach is the include graph (Section 3.1), since a module can name only what its compilation unit admits, and that admission is a compile-time fact of the same kind. Together they bound what the module can address at all; the traversal records what it did address. The difference is small, enumerable, and non-empty only where a module reached for a capability it did not use.

Graph shape carries the same information at finer grain. The traversal’s recurring two-level unit (Section 4.2) means a capability declared but never exercised appears not merely as an unset bit but as a unit that fails to expand where the declared surface says it can: a root that resolves to nothing happened against a relation row asserting that something can. A handler whose observed shape terminates at the first level against a declared surface supporting the second is visible without knowing what condition would have triggered it. Because deduplication occurs only at the root, path provenance survives the traversal, and the differential is path-sensitive rather than merely edge-sensitive — the same transition reached from an unusual position is a distinct unit rather than a merge into an existing one.

The differential is a computed field on the sandbox report, not a matter of an operator noticing something in a graph viewer. A non-empty difference is a reportable finding; a large one routes to review of the submission and the account rather than returning as a developer-facing diagnostic. Not every unexercised edge is hostile — error paths and defensive branches produce them routinely — which is why this is a flag requiring explanation rather than a verdict, and why its value lies in the flag list being short and bounded rather than open-ended. The graph inspection tooling that renders the same information navigably is part of the time-travel debugger (Section 5.6.1), which also allows execution to be run to and halted at any point in a given trace.

A module that constructs entity structure from a filesystem tree has a causal shape that is a function of what was on disk at traversal time. A module that mints a child per inbound connection is traversed with whatever traffic the sandbox presented, which by default is none. More generally: exhaustion bounds what a module can say, structurally and permanently. Bounding what a certified interior may do is not an exhaustion property. It is an admission property, resting on the sandbox report, the coverage differential, the negotiation record, the account behind the submission, and the operator’s veto — which is what Section 5 describes, and which is a human and economic mechanism rather than a decidability one. The architecture spends its enforcement budget at the gate; it does not claim the gate is a proof.

4.6 Nondeterminism as Structural Failure

In conventional systems, nondeterminism causes subtle bugs. In ETCS, it causes one of two hard failures: branch explosion instability, where different traversals produce different reachable causal graphs and exhaustion cannot converge to a stable closure; or trace non-equivalence, where the graph shape is identical but the canonical hashes differ. Either prevents admission.

These characterize stage-one failure, where nondeterminism is a property of the module’s causal structure and rejection is a technical result: the developer receives the divergence and resubmits.

Failure during the submission-triggered fuzzing campaign is handled the same way. A data value that produces divergent causal state across runs is a defect in the module’s handling of its one content channel, and it returns to the developer as the diverging value together with the traces it produced. That the developer had staked a submission on the module changes the cost to them — the submission is spent and review does not proceed — but it does not change the character of the finding, which remains technical and correctable.

Failure at the air-gapped stage is a different finding and is not handled as a resubmission. A module that reproduced consistently through every prior gate and fails to reproduce under air-gap has demonstrated network-conditional causal behavior at the final checkpoint before release. This routes to operator review of the submission and the account behind it, not back as a diagnostic — a module cannot be iteratively debugged toward passing a test whose purpose is to determine whether its behavior changes when unobserved.

Non-closure is a finding, not a failure

A causal path that does not close is neither of the above and is not a third failure class. Under the identity view, recycling regions do not close; that divergence is expected and is reported as a memory characteristic rather than a defect (Section 4.2). Under the causal view, a path that does not close indicates state that grows without bound in the module’s own causal structure — and there are legitimate designs that do exactly this. A cache sized to a working set, an append-only record, a session table under sustained load: none of these close, and none of them should.

Non-closing paths are therefore marked explicitly in the sandbox report and carried into submission as something the developer must justify to the operator or the operator’s agent. An unjustified non-closure is not rejected automatically; it depresses the module’s memory characterization, and that characterization enters valuation and list-price negotiation (Section 5.4). A developer with a sound reason pays nothing for it. A developer without one pays in price, and in the impression left on a counterparty who can see exactly which path fails to close and why the explanation offered does not account for it.

This places the judgment at the only layer capable of making it. The pipeline can determine that a path does not close; it cannot determine whether unbounded growth is correct for the module’s purpose. That determination is a human one, made against a record both parties can read.

4.7 Formal Properties of C

The admission operator governs the ontology — the shared, LGPL trait families of Section 2.1 — and not the provided types any individual module declares. The distinction determines the scope of everything below: what cannot be contracted is the space of available constraints, because signed modules depend on the constraints they claim. What a module provides against those constraints is an implementation matter and is revisable at will.

The following are properties of the admission operator as specified. They hold once the operator is implemented to this specification and are stated here as design invariants, not as empirically measured results:

Property Description
Monotone Each valid extension Ui + 1 strictly contains Ui’s causal closure. Existing signed modules cannot be removed or redefined without breaking manifest hash checks.
Contraction-free Removing admissible transitions would fail exhaustion against existing signed modules.
⊥-absorbing Any ΔO that would introduce non-monotone change is rejected.
Cycle-free A cycle would require Ui + n = Ui, contradicting monotone expansion.

The system is a monotone dynamical system over a self-extending type lattice with a single direction of travel. Ontology bifurcation is not prevented by a check. It is not representable in the state transition semantics of the system.

4.7.1 Deprecation Without Contraction

Monotonicity as stated has an apparent cost, and it lands squarely on this document’s own complaint (Section 1.1). If nothing can be removed or redefined, every early modeling error looks permanent, and the early modeling errors are made during the period when the operator understands the domain least. A system that cannot deprecate arrives at accretion by a different road.

Two things bound the concern, and the first is a matter of timing. Monotonicity binds from the first operator signature, not from the present state of the repository: an ontology that has never been signed against has nothing depending on it and can be restructured freely, and the shipped hierarchy is still in that condition (Section 8). What follows describes the regime that begins when the first module is signed.

The rest of the concern dissolves on the distinction of Section 2.1. The monotone object is the ontology: the trait families and the constraint positions within them. A module’s provided types are not part of it. A developer who models a leaf badly, names it poorly, or splits one type where two were needed revises the module and resubmits; nothing in the admission operator is engaged, because a provided type was never a commitment the ontology made. The permanence that monotonicity imposes applies to the vocabulary of constraints, not to the population of things claiming them, and the large majority of ordinary modeling error lives in the latter.

What remains is genuine. An ontology node genuinely modeled wrong — a family split at the wrong branch point, a constraint that should have been two — cannot be withdrawn once modules have been signed against it. Every ontology of consequence has needed a path here: Dublin Core, schema.org, and HL7 FHIR all required deprecation, and none of them found the need optional.

ETCS’s answer is that deprecation is an addition rather than a contraction, and therefore costs the monotonicity property nothing. A superseded node is not removed and no signature against it is invalidated; it acquires a tombstone: a Superseded marker carrying a reference to its replacement, the identity of the party who marked it, and the timestamp of the marking. The tombstone retains the observer. Existing signed modules continue to verify, because nothing they were built against has been withdrawn. Exhaustion against them continues to pass, because the admissible transition set has grown rather than shrunk.

What changes is everything downstream of the ontology rather than inside it. Tooling reports a tombstoned node as superseded and names the replacement. New module submissions claiming one receive a diagnostic, and the operator may decline to sign against it as a policy matter — a decision at the admission layer, which is discretionary, rather than at the closure layer, which is not. A tombstoned lineage may be excluded from the default SDK tier without ever being removed from the ontology, so that new authors do not encounter it while existing consumers are undisturbed.

The result is that the ontology accumulates its own history rather than editing it. This is more storage and more tooling burden than deletion would be, and it is the correct trade: the cost of a permanent record is bounded and known, whereas the cost of a contraction is a break in every signature that depended on what was removed.

4.8 Extension to AI Action Confinement

Nothing established in Sections 3 and 4 is specific to human-authored modules. Any caller driving the ETCS call interface — a third-party AI system issuing .etcs traces, or the ETCS-native AI planned for the platform — is confined by the same two mechanisms as any module author: it can name only what its ontology grants, and it can say only what the grammar expresses.

The consequence for explainability follows without further machinery. An AI operating through ETCS produces traces drawn from the same bounded space exhaustion traverses for any module, so explainability is a property of the substrate the agent is confined to rather than an interpretability layer added over its behavior. Like the pipeline itself, the tooling that would exhaust an agent’s space is target infrastructure (Section 8).

The scope is the scope of everything above it: what an agent can express, not what an interior does once invoked, with data content sampled rather than exhausted (Sections 4.5, 4.9). Anticurrent Entropy Inc. intends to govern its planned ETCS-native AI by this machinery rather than by a separate, purpose-built safety layer.

One terminological note, since the next section uses the word differently. Every agent here is an AI system driving the call interface. An ACE agent (Section 5.4) is a person authorized to act on the company’s behalf, and carries no AI sense whatever.

4.9 Known Limitations

The claims of this section rest on stated conditions and have stated limits. What remains open is genuinely open, and it is also narrow: each item below is bounded by an existing causal structure of the substrate rather than by an appeal to future work. They fall into four kinds, and the kind matters — a limit on what a certificate covers is a different thing from a figure that is measured rather than derived.

What the certificate covers.

Causal shape is exhausted; data content is sampled. This is the load-bearing scope limit and the one to read first. The traversal is exhaustive over the reachable causal state graph. The data channel is covered by coverage-guided, structure-aware fuzzing (Section 4.5), which is a sampling procedure and is not represented as anything else. A handler that branches on one specific value handles every other value deterministically and passes the determinism criterion while doing so. The certificate is consequently a hybrid object: exhaustive in one dimension, sampled in the other, and stronger than either description alone would suggest — but it is not exhaustive in the unqualified sense, and the document does not claim it is. What bounds the sampled dimension is that data is the only content channel there is; the sample is taken over a known space rather than an open one.

Closure is closure of the projection. The traversal walks the projected state defined in Section 4.2, not a module’s total state. Interior state that gates surface behavior — a connection flag, a transaction flag — and effects outside causal state, such as rows written to a backing store, are projected away. A cycle can therefore be reported for a module that has in fact moved on, and two runs whose divergence lives entirely in the projected-away part are compared as identical. This is not the same limitation as the interior one that follows: that one concerns what a certified module may do, while this one concerns whether the state-identity relation the traversal uses is fine enough for the closure result to carry the weight it appears to. The result is sound as a statement about the projection and is not a statement about the module.

Exhaustion certifies the horizon, not the interior. The interruption contract closes the degenerate case in which an interior conceals behavior by not returning. It does not close the case in which an interior returns promptly and behaves differently under conditions the pipeline does not vary. Section 4.5 tabulates which conditions those are. Interior trust is established at admission by non-decidability-based means.

What the instruments can and cannot see.

Declared-but-unexercised capability is detected, not resolved. The coverage differential identifies that a module reached for a transition it never performed. It does not identify the condition that would perform it, and it does not distinguish a dormant trigger from an error path. It converts an open-ended search into a bounded flag list requiring explanation, which is a genuine improvement over having neither, and is not a proof of absence.

The differential detects unreached capability, not unreached depth. A recursive construction sets one bit and clears it at first use: a type that mints its own kind exercises that self-edge at depth one, and the differential is empty from then on however far the recursion would have gone. Capability that is reached shallowly and would behave differently deeply is invisible to this instrument, and it is a common shape rather than an exotic one — anything that walks a tree has it. Depth coverage is a property of the traversal’s reach, reported alongside the differential rather than certified by it.

Environmental input is neither controlled nor varied. Where a module derives causal structure from its surroundings — an entity tree built from a directory, children minted per inbound connection — the traversal characterizes it against whatever the sandbox presented. That is one environmental sample, not a bound, and the population figure below is measured against it. Controlled fixtures and traffic variation are compatible with the architecture and are not built (Section 4.5).

What is measured rather than derived.

Concurrent live population is measured, not derived. Producer-minted population closes by cycle wherever the tooling detects closure, and the high-water mark observed during traversal is carried on the certificate. No compile-time ceiling on concurrent live population exists or is claimed: how many children a producer holds live is a property of its interior under external drive, bounded by arena capacity and a deterministic halt rather than by a constant readable from the binary. A module whose production discipline differs in deployment from what the traversal exercised is characterized on what was observed.

The allocation class set is fixed but not statically enumerable. That arena high-water mark tracks concurrent live population rests on every allocation shape recurring, which follows from the routing described in Section 4.2: sub-arenas forward to a single module arena, the fixed shapes are the declared types and the interior’s structs, and variable-length data is carried by the transport primitive rather than allocated. What does not follow is advance knowledge of the class set. The declared types are readable from the export horizon; the interior’s struct shapes are ordinary C++ and are not. A module’s memory characterization is therefore measured over the traversal rather than derived from the binary before it runs. That is where the sandbox report places it in any case, but the figure is an observation rather than a computed ceiling, and a module whose interior allocates shapes the traversal did not exercise is characterized on what it did rather than on what it could.

Traversal growth is expected to be bounded and has not been measured. The structure the measurement would run against exists today: the relation matrix is populated at compile time in every compiled module, and the traversal’s recurring two-level unit is determined by the substrate rather than by tooling. What does not exist is anything that reads it, and the reason is that current modules do not declare enough types for the question to be interesting. Reading it is a front-end task rather than an architectural one (Section 8). The expectation — that the traversal unit is the composition unit of Section 2.1.1 recurring at a second scale, and that growth is therefore governed by the same closed algebra rather than by a free product of choices — is mechanistically motivated and structurally consistent, and it is an expectation. Whether it holds at full type capacity with deep mutation chains is an empirical question awaiting a module wide enough to pose it.

What rests on trust rather than structure.

The verifier is trusted code. The exhaustion pipeline, the fuzzer, the sandbox, and the hypervisor monitor are themselves implementations and are themselves subject to soundness defects. A certificate is only as good as the instrument that produced it, which is among the reasons Section 5.6.1 argues for making the verifying instrument broadly held rather than rare.

Review capacity is bounded and the bound is unmeasured. The admission criterion is a single question asked against a computed report rather than against source (Section 5.4.1), which makes clean submissions cheap to judge and keeps cost independent of module size. It does not make flagged submissions cheap, and the flagged fraction of a real corpus is unknown because no corpus exists. The exposure is concentrated further by there being one reviewing authority: a single party’s availability bounds marketplace throughput, and that is a key-person dependency in the ordinary sense as well as a structural property of having one signing key. The Linux kernel establishes that such a dependency is compatible with adoption at the largest scale, and that review delegates down a maintainer tree while final authority does not (Section 5.4.1). It does not establish that the exposure is absent, and the failure here is costlier than a kernel’s because what is admitted carries a behavioral guarantee rather than a merge.

Signing is centralized by design. Section 5.8 states this as the moat and Section 5.8.2 addresses the witness-independence problem it creates. It is a market structure, not a technical guarantee, and it is the property most likely to be a legitimate objection from a reader who accepts everything else in this document.

5. Marketplace Architecture

What follows is the marketplace and signing model as designed; it depends on the certification pipeline of Section 4.5, whose deployment status is Section 8’s.

One criterion governs admission, because quality and malice are not two of them. A conventional platform signature attests provenance — this artifact, from this author, unmodified — and makes no claim about what the artifact does, which is why quality and hostility are separate concerns there. An ETCS signature attests behavior: the certificate states that a module’s causal structure is exactly the enumerated one, and a user’s reason to trust the module is that the operator verified that claim. A module that is merely bad — state that grows where nothing in its record predicted it, a surface that does not do what its constraint set implies, resource behavior the sandbox report does not account for — has produced the same outcome as a hostile one. A user relied on a guarantee that did not hold. Intent differs; the damage to the signature does not, and under redundant witnessing what is being observed is whether the signature means anything at all. Review therefore asks one question rather than two: does the artifact match its record.

Trust in a module’s behavior is therefore an admission property, not a runtime-confinement property. The substrate bounds what a module can express (Section 3); the admission pipeline and distribution authority bound what is trusted to run at all. A module reaches a user’s Tier 1 runtime only by being pulled from the marketplace, and pullability is itself gated on certification — so an implementation the operator would not sign is not a runtime hazard to be contained but an artifact that never enters distribution. The interior of a certified work function is unconfined at runtime because its scrutiny has already happened, at the one point in the lifecycle the operator fully controls. Runtime confinement of certified code would defend against a threat the admission gate exists to exclude; the architecture spends its enforcement budget at the gate instead. The verifying instruments of Sections 4 and 5.6.1, the coverage differential of Section 4.5, and the transparency log of Section 5.8.2 exist to make that gate’s decisions reproducible and inspectable rather than taken on authority — which is the same property, applied to the operator itself.

5.1 The Operator as Causal Authority

Section 3 establishes that a module’s expressible causal reach is fixed by the headers in its compilation unit. The marketplace is the party that decides which headers go into which module tier’s SDK, and that is the whole of its authority over authorship: it is not policing behavior after the fact but setting what is possible before compilation.

The trust boundary is therefore a distribution event with a date and a manifest, rather than a permission system with a runtime surface — which is what makes it auditable in a way no runtime check is.

5.2 The Signing Authority

Module signing is a statement about the bounded causal graph of Section 4.4, not an open-ended behavioral claim: the signature asserts that the operator performed the traversal and obtained this result. What makes it checkable rather than authoritative is established there — any party holding the module and the public ontology can perform the same traversal, and every issuance is publicly recorded (Section 5.8.2). The operator’s signature is the one the ecosystem has agreed to price, not the only one that can be produced.

5.3 Runtime Trust Configurations

Section 5.1 governs what a module can be written to do. This section governs a separate and independent axis: which signing keys a runtime instance will admit at load time, and therefore what a user’s installation can be made to run.

A runtime instance exists in exactly one of two trust configurations at any time.

Tier 1 — First-Party (default). The distributed runtime (Section 1.5) carries the marketplace signing key embedded in the loader itself. In this configuration — the default, and the only configuration reachable without an explicit acknowledgment — the runtime admits only modules signed by that one key: the LGPL free-tier corpus (Section 5.4) and any paid marketplace modules, both certified through the same operator signature and both recorded in the transparency log (Section 5.8.2). This is the smallest expressible attack surface in the system: one key, one certified corpus, no admission path for anything else, and no cost to enable it. Single-key admission and the load-time handshake (Section 3.2) are properties of the runtime binary today; the certified-corpus half comes into force with the pipeline (Section 8).

Tier 2 — Self-Signed Development. The distributed runtime admits only the embedded operator key by default, and enabling any additional key requires an explicit, recorded acknowledgment that the resulting instance falls outside the closed-graph guarantee of Tier 1. That acknowledgment is the whole of the gate: it costs nothing, requires no purchase, and is available to every holder of the runtime. Nothing in the licensing or distribution of the runtime conditions a developer’s ability to build modules against CORE and ONTOLOGY — modified or unmodified — and run them.

On activation, the instance generates its own signing key, trusted by default within that instance, so a developer can sign and run their own modules locally ahead of submission to causal exhaustion (Section 4). The capability is scoped to the specific runtime instance in which it is activated, not to a developer’s account as a whole: a developer may run one Tier 2 instance for local development alongside an otherwise-ordinary Tier 1 instance without affecting the latter.

Paid marketplace modules are unavailable for the duration of this configuration. The risk being addressed is concrete: a module running under a locally generated key has not been exhausted, and unexhausted code sharing a process with certified modules can reach a provider surface that was exhausted on the assumption no such neighbor existed — through a header or ABI mismatch, or a hand-assembled syscall issued by code the pipeline never verified.

That risk is technical, and it does not distinguish paid modules from free ones. The free-tier LGPL corpus remains available in Tier 2 regardless, and the reason is a deliberate trade rather than a containment argument: a development configuration with no modules available is not a development configuration, and the free corpus is the minimum a developer needs to build against. What withdrawing paid access protects is narrower and is the part worth protecting — a purchased module carries a guarantee the operator made to a paying user, and running it beside unverified code voids that guarantee without the user having agreed to it. The free corpus carries the same certification and no purchase, so the same technical exposure remains and is accepted. It is disclosed here rather than described as contained.

The two postures are mutually exclusive by construction: a runtime instance cannot simultaneously assert “every module I run has passed certified exhaustion” and “I will run whatever key I or a third party points me at.” Tier 2 exists so that development has a sanctioned home inside the runtime rather than being pushed into an unobservable fork. The independently built loader of Section 3.4 is not a third tier; it is the boundary of this model.

Note the ordering: security decreases monotonically as admitted capability increases, and the least secure tier is the only one requiring an explicit, recorded declaration to enter, while costing nothing to reach. This is inverted relative to typical software distribution, where security is commonly a paid tier and the insecure configuration is the unremarked default.

5.4 Economic Model

Causal exhaustion (Section 4.4) produces more than a pass/fail admission result for a submitted module. Where a candidate module’s causal structure fails to exhaust cleanly, the pipeline returns the specific invalid .etcs traces themselves, as executable scripts: a developer receives not a report describing a defect, but the exact reproduction of it, deterministically re-runnable against their own source on their own machine. Where exhaustion succeeds, the same pipeline produces a sandbox report characterizing the module’s certified trace set: the closure structure of its state graph under both views, with any non-closing paths marked (Section 4.6); the coverage differential between declared and exercised capability (Section 4.5); the performance and resource characterization described in Section 2.9; and the concurrent live population at which the traversal was run (Section 4.9).

This sandbox report is not returned to the developer alone, though holding a passing one changes nothing by itself. A passing report is what qualifies a module for submission; submission is a separate act the developer takes, and it is that act which opens the review process and creates a dedicated thread within the ACE Guild Forum. Modules that fail exhaustion or the sandbox baseline remain private diagnostic feedback to the developer (Section 5.8.1) and cannot be submitted at all — there is no thread, public or private, for a module that has not yet passed, and none for a passing module whose author has not yet chosen to take it to market.

Submission opens the one-day fuzzing window described in Section 4.5, so the thread’s starting material is the post-fuzz report rather than the pre-submission one. A reviewer responds within two weeks of that window closing; a submission still on the backlog at that point is reviewed by the operator directly. Once created, the thread is initially private, visible to the operator (or, later, an ACE agent) and to the developer’s own account — the same account through which it is trivially reachable from their forum profile — and is published in full once the module becomes available on the marketplace. The thread is locked as a record rather than an open discussion: the sandbox report and causal trace set are posted as its starting material, and either side may open negotiation at any point once the thread exists, but the record itself is not edited or re-litigated. It serves as the shared factual anchor for everything that follows: a timestamped, exhaustive statement of exactly what the module does, established before either party negotiates over what it is worth.

Price negotiation proceeds from that anchor rather than from assertion by either side — the causal exhaustion report is the transparent negotiation basis referenced in the table below, not a supporting document alongside one. The negotiating counterparty is the operator directly during the marketplace’s early corpus and, once a sufficient body of prior negotiations exists to constitute working precedent, may be an ACE agent operating against that precedent corpus.

An ACE agent is a person authorized to act on Anticurrent Entropy Inc.’s behalf — the term is used here in its ordinary commercial and legal sense, as in an agent of a firm. It is not an AI system, and it is unrelated to the AI material of Section 4.8 or to the ETCS-native AI planned for the platform. An agent reads submissions, applies the accumulated precedent of prior negotiations, and negotiates within it; final authority remains with the operator, who retains the veto described below. Delegation of review to agents is the throughput mechanism discussed in Section 5.4.1, and it is delegation of reading rather than of signing — the signing key is not delegated at all (Section 5.8). That precedent corpus is drawn exclusively from threads that have already gone public; a still-private, in-progress negotiation is never visible as precedent for a different developer’s negotiation, public or otherwise. A developer may still escalate any negotiation to the operator directly regardless of counterparty. The operator retains veto authority over the outcome; the standard applied to an escalation scales with the soundness of the reasoning behind it, not with the fact of disagreement itself, so a well-founded dispute is not penalized for having been raised, regardless of how the underlying negotiation is ultimately resolved. What tightens as agent-mediated negotiation becomes the norm is the bar for what constitutes a founded escalation, not the operator’s willingness to hear one — direct review remains fully available to a developer with a real case, and proportionally less available to an escalation raised without one.

Justifications offered for non-closing causal paths (Section 4.6) are precedent-generating in the same way as any other negotiated outcome. A reasoning accepted for one module’s growth path enters the corpus once its thread goes public and is available to the next developer whose module grows for the same reason. The standard for what constitutes an acceptable justification therefore tightens by accumulation rather than by fiat, and a developer facing an agent counterparty is facing the accumulated record of what has previously been accepted rather than an undocumented judgment.

Negotiation concludes in a list price, and the price is set by the operator rather than by the developer or by agreement between them. The thread is where a developer makes their case from the exhaustion report; the veto described above is the same authority exercised at the point of decision rather than only on appeal. What the process produces is an informed determination, not a bilateral contract, and a developer who believes the determination is wrong escalates on the terms already stated.

The developer may then convert that list price, in whole or in part, into worker-tier stock (Section 5.5). The conversion rate is set once a year from the previous year’s realized worker-pool distribution — the dividend actually paid, not a projection of the next one. A developer therefore knows the rate before choosing to convert, and the rate is anchored to value the pool has already delivered rather than to a forecast of value it might. Marketplace release follows the air-gapped reproduction described in Section 4.5, which runs once at this point rather than per submission.

A developer who converts the entirety of a module’s list price to worker-tier stock forgoes listing revenue entirely; in exchange, the module is released at no cost and is automatically relicensed under LGPL, joining the free-tier corpus described in Section 5.3, Tier 1. The developer is compensated in equity rather than in price.

This is the mechanism by which the free-tier corpus grows over time without depending on donated labor: a module moves from proprietary and priced to open and free as a single, developer-initiated conversion, compensated through participation in the platform’s own success rather than through direct payment for the module itself. Anticurrent Entropy Inc. refers to this internally as the Anticurrent Entropy cycle: proprietary value converting back into open, shared corpus, funded by growth in the whole rather than extraction from any one part.

5.4.1 Review Capacity and Its Bound

What this means for a developer is turnaround: how long between pressing submit and hearing back. Section 5.4 states the commitment — a one-day fuzzing window, then a response within two weeks, with the operator reviewing anything still on the backlog at that point. What follows is why that interval is sustainable rather than optimistic, because the criterion is one question rather than two and it is asked against a record rather than against source.

What a reviewer reads is not a module’s implementation. It is a structured artifact with computed fields: the horizon as enumerated, the closure structure under both comparison views, the coverage differential between declared and exercised capability, the memory and performance characterization, and the fuzzing result. Every one of those is produced mechanically. The reviewer’s work is to judge whether the artifact matches its record and whether anything the report flags has an account behind it — not to read code, and not to form an opinion about implementation quality that the report does not already carry. Review time is consequently governed by the report’s flags rather than by the module’s size or complexity, which is why a large module with a clean report is cheaper to review than a small module with an unexplained growth path.

Cost is therefore bimodal rather than proportional. A clean report is fast, and most reports will be clean, because a developer reaches submission only after iterating against the same pipeline until they were willing to stake a submission on it. A flagged report is slow, and its slowness is irreducible: a non-empty coverage differential with a plausible justification behind it is exactly the case where the mechanical inputs have been exhausted and judgment is the remaining instrument. The operative bound is the flagged fraction multiplied by the depth a flagged case demands, not throughput per module.

That bound is real and is not currently measurable. The flagged fraction is unknown until a corpus exists, and the deep case does not become cheaper with volume — precedent teaches an agent what past acceptable submissions looked like, and the cases that matter are the ones that do not resemble those. The commitment this document makes is the response interval stated in Section 5.4 rather than an unbounded capacity claim, and if the flagged fraction proves higher than expected, the response interval is what gives first. Anticurrent Entropy Inc. would rather lengthen a stated interval than dilute the standard the interval exists to apply.

Two further observations belong here rather than in a footnote. Review is not a role staffed against a job description; the party performing it authored the ontology being judged against and builds the instruments the report is produced by, which is a different position from a reviewer hired to apply someone else’s criteria, and one whose throughput is not estimable from conventional review metrics. That is an argument about the shape of the work, not a claim about any individual’s capacity, and it does not remove the key-person exposure that a single reviewing authority creates — which is stated as such in Section 4.9 rather than argued away here.

The configuration is not unprecedented, and the precedent is instructive in three separate respects. The Linux kernel operated for three decades with a single final authority over what was merged, under a copyleft license that made forking legally trivial and technically routine, and became the most widely deployed kernel in existence over that period. Concentration of final judgment did not prevent adoption, and is frequently credited with the coherence that made the adoption worth having. Forks were numerous and essentially none were undertaken to escape the gatekeeper, because what a fork copies is the code and what it cannot copy is the set of parties who have agreed to trust the result — which is the argument of Section 5.8.1 stated as history rather than as prediction. And the throughput problem was solved by delegating review down a maintainer tree while final authority remained undelegated: subsystem maintainers read patches, and the top of the tree merged from maintainers rather than from contributors. That path is open here: the review pipeline feeding the signing key is delegable even though the key is not (Section 5.8), and the agent-mediated review of Section 5.4 is one instance rather than the only available one.

The disanalogy is worth stating alongside it. A merged kernel patch is not a behavioral guarantee made to an end user, and a defect admitted to Linux is a bug its users may encounter and fix, because they hold the source and the authority to change it. A defect admitted here is a guarantee that did not hold, made by the operator to a party who relied on it — which is why the criterion above collapses badness into hostility, and why this review standard cannot be relaxed in the direction a kernel’s can. The precedent establishes that a single final authority is workable at scale and that review delegates while authority does not. It does not establish that the failures of this configuration cost the same as that one’s.

5.4.2 Purchase Pricing and Dependency De-duplication

A module’s list price is what it costs a user to hold that module, not what it costs to run any particular thing built on it. The distinction matters because ETCS makes dependency explicit: a module can address only types whose headers it was built against (Section 3.1), and its export horizon names what it provides. The set of type providers any purchase requires is therefore computable from the artifacts themselves, before the purchase.

Purchases are priced over that dependency closure, less what the user already holds. A user buying their first game built on the Vale engine pays the engine’s list price and the game’s. A user buying a second, unrelated game built on the same engine pays only the second game’s price, because the engine is already theirs. Nothing is charged twice, and the de-duplication is mechanical rather than a discount policy — it falls out of dependencies being nameable rather than being a concession the operator grants.

Two consequences follow, and both run in the ecosystem’s favor.

A type provider is bought once per user, not once per downstream module. A widely depended-upon provider is reached by many users, since any module requiring it triggers the purchase for a user who lacks it, while no user pays for it more than once. Foundational work earns across the breadth of what depends on it without taxing each thing built on it, and a developer choosing between shipping a provider and shipping a leaf is not penalized for building the more general artifact.

Converting a foundational provider to the free corpus is worth more than converting a leaf. A developer who converts a provider’s entire list price into worker-tier stock releases it free and LGPL, which removes that provider from every downstream dependency closure, for every user, permanently. The author is compensated in equity whose value tracks the ecosystem as a whole, and the ecosystem gets a cheaper floor for everything built above that provider. This is the Anticurrent Entropy cycle at its most direct: the conversion that costs a developer the most listing revenue is the same conversion that most reduces the cost of everything downstream of it.

5.5 Equity Structure: Shareholder and Worker-Tier Stock

Throughout this document, the ACE guild refers to the set of holders of currently participating worker-tier stock in the ACE ecosystem (Section 5.5) — primarily developers who have earned that stock by converting a module’s list price under Section 5.4, and who share in the annual worker-pool distribution for as long as they hold stock still within its participation window. Guild membership is thus a live property of currently held, still-locked worker-tier stock rather than a permanent title: a holder ages out of it as their stock converts to ordinary shareholder equity at the end of its lock (Section 5.5) and ceases to participate in the pool. This is a governance-and-equity term specific to Anticurrent Entropy Inc.; it is unrelated to any in-fiction “guild” mechanic in the Vale narrative world described in the accompanying philosophy paper.

If you convert a module’s list price into stock rather than taking payment, this is what you are holding. Anticurrent Entropy Inc. issues two classes of equity, which together form a single system rather than two unrelated instruments. Shareholder stock is standard equity in the company: liquid, transferable, and outside the worker dividend pool described in Section 5.4. Worker-tier stock is the instrument developers receive by converting a module’s list price under the mechanism described in Section 5.4; it participates in the annual distribution of the worker stock pool, and is locked for a five-year term during which it is not freely transferable.

The two classes convert into each other at opposite ends of the same term. Shareholder stock can be converted into worker-tier stock, trading liquidity for participation in the pool and entering the five-year lock. Worker-tier stock converts automatically into shareholder stock at the end of its five-year vesting period, at which point it becomes liquid and ceases to participate in the pool going forward. Value does not sit in a separate account depending on which side of that conversion it is on — it is the same equity, differently liquid depending on where it sits relative to the five-year term.

5.6.1 The Debugger as Verification Instrument

Section 4.4 establishes that a module’s causal trace set is a proof object rather than an attestation. This is not merely a claim about what the language makes possible in principle: re-executing a recorded .etcs sequence already reproduces an identical causal-state trace today, via the REPL shell (Section 8), because the sequence is deterministic over exactly the causal state described there.

The time-travel debugger is the instrument that makes that determinism usable rather than the source of it. It provides four things over the raw shell reconstruction a user would otherwise work through by hand: a graphical, navigable presentation of causal replay, with execution able to be run directly to and halted at any point in a recorded trace; step-backward traversal with full causal-state inspection at each point; a graph inspector rendering the deduplicated state graph under both the causal and identity views (Section 4.2), with closed regions marked as cycles and non-closing regions marked explicitly as infinities, alongside the coverage differential of Section 4.5; and a continuous verification filter over any module loaded under a non-operator key, checking causal-state conformance for as long as that module runs rather than once at load.

The last of these is what makes the debugger a verification instrument and not only a development convenience: under a self-signed key the developer’s own machine is the only thing checking anything, and the filter is what does the checking. The graph inspector matters for a second reason. It renders the same findings the sandbox report computes, which means a third party holding a module can recompute the closure structure and the coverage differential rather than reading the operator’s summary of them — the reproducibility argument of Section 4.4 made operable rather than merely available in principle.

The debugger is a paid product, and self-signing (Section 5.3, Tier 2) is not gated behind it. Pricing the debugger as broadly accessible, once built, is a deliberate choice to make both the filtering capability and the recomputation capability ubiquitous among the runtime’s user base rather than concentrated among users sophisticated enough to build an equivalent themselves. A trust model whose verifying instrument is rare is a trust model that functions only for users willing to trust on authority alone, which is the exact posture this architecture exists to avoid. That reasoning applies with equal force to the instrument’s price and to its availability, which is why the ability to run one’s own code is not part of what is sold.

Both the continuous filter and the graphical interface are target architecture at this stage: the underlying causal-replay determinism they depend on already works; the debugger that packages it into a usable product does not yet exist.

5.7 Bootstrapping via Existing Open Source

The marketplace’s cold-start supply problem has a direct answer in existing C++ open source. A maintainer of an existing C++ library can expose its functionality as an ETCS type provider by writing a conforming work function and type header against the ontology — an adapter, not a rewrite. Doing so is straightforward specifically because the library is already C++; it does not generalize to open source written in other languages without a bridging layer this document does not claim to have solved.

Once conforming, the library receives causal exhaustion at no cost to the maintainer. This is a narrower claim than blanket testing of the library’s internals: exhaustion certifies the export horizon — the .etcs causal state reachable against it (Sections 2.7, 4.2) — not the Turing-complete implementation behind it, for the reason established there and bounded in Section 4.9. What the maintainer receives is an external, hash-certified verification of their module’s causal interface, produced as a side effect of marketplace admission rather than as a paid service.

A maintainer who intends their module to remain LGPL, as is common in existing open source, can convert its list price into worker-tier stock under the mechanism described in Section 5.4 rather than collecting revenue directly. In effect, an existing open source project can use marketplace admission as external verification that pays in equity rather than in listing revenue — a supply-side path into the ecosystem that does not require a maintainer to abandon the license terms they already publish under.

The arithmetic is unusual enough to state plainly. An existing C++ library earns its maintainer nothing directly. Writing a conforming type header and work function is an adapter rather than a rewrite. Submission consumes a build-server allowance the free tier already provides (Section 5.9). The operator sets a list price on the result, and converting that price in full yields worker-tier stock while releasing the module free and LGPL into the corpus every runtime can load. The maintainer ends holding equity that participates in the annual distribution, and a hash-certified external verification of their causal interface, for work that previously returned no revenue at all — and under the de-duplication described in Section 5.4.2, a library that many modules depend on is acquired by many users rather than earning once.

5.8 Defensibility of an Open Substrate

The ontology being LGPL does not weaken the marketplace’s defensibility; it is what the defensibility is built on. The asset that matters is not the code, which is public, but the admission operator described in Section 5.1 and the signing authority described in Section 5.2 — the certified position of being the sole party whose causal exhaustion and header distribution a module must pass through to be trusted within the ecosystem. This is a certificate-authority moat, not a code-scarcity moat: it does not depend on withholding the ontology, and it is not weakened by anyone being able to read, fork, or reimplement it. It depends on being the operator whose signature the ecosystem has agreed to trust — and that position cannot be partially delegated without collapsing the guarantee it provides, which is why the review pipeline feeding the key is delegable (Section 5.4.1) and the key itself is not.

An open substrate is, if anything, a precondition for this model rather than a risk to it. A closed ontology would require developers to trust an opaque authority; an open one lets every participant verify exactly what the operator is and is not certifying, while still requiring that certification to pass through a single, auditable point of authority to carry any weight in the marketplace.

5.8.1 Why Forking Remains Available and Rarely Chosen

Carrying no guarantee is not the same as carrying no value. A rational developer nonetheless has little reason to build a private loader, whatever the option’s legal availability (Section 3.4), and the reason is economic rather than legal.

Every developer account, at no cost, may submit a module against the causal exhaustion pipeline a bounded number of times per day, each executed in an isolated, per-submission sandboxed build environment. Each submission returns one of two things: certification, or the exact set of invalid .etcs traces the module’s structural deficits produced — reproducible, executable scripts, together with explicit reasoning identifying which invariant each trace violates and an automatically generated plain-language summary of the finding. This is materially more than a pass/fail signal; it is the same diagnostic a developer would otherwise have to reconstruct by hand, provided free as a byproduct of ordinary iteration.

In practice the iteration a structural deficit requires does not consume submission capacity at all. A returned invalid trace is an executable script that reproduces the defect deterministically on the developer’s own machine, against their own source, under a self-signed instance — the fix is developed locally and verified locally, and the build server is contacted again only to certify the result. Submission volume tracks completed modules, not debugging cycles. Developers who need more than the free allowance provides may purchase additional per-build submissions above the daily maximum at cost (Section 5.9).

Against this, the value proposition of a private fork is difficult to construct. A forked loader must reimplement, unassisted, the diagnostic capability the free tier already provides at no cost — and having done so, it still produces a module admissible only into a runtime nobody else has reason to trust, carrying none of the guarantees described throughout this document. There is no scenario in which building a private pipeline is cheaper, faster, or more informative than submitting against the real one. Submission is not merely permitted; for a developer actually trying to ship a correct module, it is close to strictly dominant.

Accounts found to misuse the submission process are suspended.

5.8.2 The Transparency Log

A single signing authority creates a specific epistemic problem that is better named than left for a reader to find. Section 4.4 establishes that anyone can recompute a certificate; Section 5.2 establishes that only the operator can make one count. The consequence is that the ecosystem’s record of what has been admitted has many copies and one origin. High copy count with a single origin is not the same as independent corroboration, and a reader who takes the reproducibility argument of Section 4.4 seriously will observe that reproducibility at the verification layer does not by itself buy independence at the admission layer.

Certificate Transparency is the established answer to precisely this structure in the web PKI, where issuance is likewise centralized and likewise had to be made accountable without being distributed. ETCS adopts the same mechanism. Every admission — the module hash, the target it was built and exhausted against (Section 4.4), its declared ontology surface, its certified trace set hash, the exhaustion parameters including the concurrent live population actually instantiated (Section 4.9), and the operator signature — is appended to a public, append-only, cryptographically verifiable log. A signature that does not appear in the log is not honored by the runtime. Any party may mirror the log, recompute any certificate in it against the module it names, and publish a disagreement. The log’s append-only property is itself verifiable by any mirror without trusting the operator, which is the whole of the mechanism’s value.

This does not federate the signing key, and it is not intended to. The operator remains the sole admission authority, for the reason given above. What the log changes is that the operator’s decisions become externally checkable after the fact by parties who share none of the operator’s interests. Misissuance becomes detectable rather than merely deniable, and the difference between trust the operator and verify the operator becomes a mechanism rather than a disposition. The moat survives intact; what it stops being is unaccountable.

The log is target infrastructure and is gated on the same build-server deployment as the certification pipeline (Section 8).

The rate limits are calibrated to that cadence rather than against it. A submission does not return a pass/fail signal; it returns a complete trace set — the covering traversal, and where exhaustion failed, the specific invalid traces as executable scripts (Section 5.4). That is a substantial diagnostic artifact, and working through one properly occupies a developer locally for a considerable stretch. The intervals between submissions are sized to the realistic duration of that work, not below it. A developer who genuinely exhausts a trace set’s diagnostic content faster than the free interval permits is working at a pace the paid tiers and on-demand credits exist to serve, and is by that point well past evaluation.

The Guild tier is where Section 5.4’s conversion mechanism acquires a second dimension. A developer converting a module’s list price into worker-tier stock receives not only participation in the annual distribution but elevated certification throughput at no subscription cost — an operational benefit realized immediately, alongside an equity benefit realized over the five-year term. Alignment is compensated on both horizons rather than only the long one.

Submission capacity is subject to the abuse provision already stated in Section 5.8.1. Enforcement escalates from rate limiting to account suspension; the operator reserves the right to refuse service to accounts demonstrating patterns consistent with attempts to probe or exhaust the certification pipeline rather than to certify modules.

The differences are that capability boundary, type identity, and ABI contract are one artifact here rather than three coordinated ones, and that admission is gated on a certified traversal rather than on the import list. Erlang / OTP Independently arrived at nearly the same isolation model: isolated state machines, unrestricted internal cycles, message passing at boundaries, location transparency. This document therefore does not call its certificates proof-carrying. What the two share is the commitment underneath — a consumer positioned to establish a claim rather than accept it.

9. Conclusion

The problems Section 1.1 opens with share a generative source, and unifying the artifacts that produce them does not solve those problems so much as stop generating them.

What that buys, concretely, is a system whose internal consistency does not degrade under extension. A new type participates fully by inheriting its lineage. A new realization of an existing constraint runs every script written against that constraint, unmodified. The ontology grows monotonically and deprecates by addition rather than removal, so nothing you build against is withdrawn from underneath you. Where the substrate’s guarantees stop — at the interior of your own work functions, at the data you pass across the one content channel, at everything Section 4.9 enumerates — it says so rather than implying otherwise.

The claim is not that ETCS eliminates the need to trust an operator. It is that what the operator asserts is small, precisely bounded, independently recomputable, and permanently recorded, which is a different and more defensible claim than a substrate of this kind is usually made to carry.

The runtime is free and the ontology and core are LGPL. The local development loop — write, self-sign, run, replay, inspect — works today and costs nothing. The debugger, Vale, and the marketplace follow on the schedule in Section 8. If you build C++ that loads code you did not write, the constraint table in Section 1.1 is the shortest statement of what changes.

Appendix A — The Trait-Base Convention, by Example

This appendix works the composition algebra of Section 2.1.1 and the surface distinction of Section 2.8 through the shipped ontology. It is illustrative rather than normative; the properties it demonstrates are stated in the body.

A.1 The Two-Header Convention

Each claimable ontology node is authored as a pair of headers. An interface header (Deletable.h, Database.h) declares a constraint as pure virtuals over a virtually-inherited Entity root. A base header (DeletableBase.h, LocalDatabaseBase.h) is the CRTP proxy a concrete leaf inherits: for each interface method it provides a complete, non-virtual outer method — which satisfies the interface and is what any caller invokes — forwarding to a fresh pure virtual the leaf must implement. The macro ETCS_DISPATCH_METHOD generates each outer/inner pair from one declaration (with ETCS_DISPATCH_METHOD_CONST for const-qualified members), so the two can never drift apart in name and every claimed method is auditable from a single call site.

A node may publish the first header without the second, and Database does. Such a node is an interior node of its family tree (Section 2.1): it declares a constraint for its descendants to refine, and no provided type claims it, because there is no base to inherit. Base headers sit at the leaves of each family tree, and the presence or absence of one is therefore what makes a node claimable — visible from the header set alone, without reading a line of source.

A naming convention separates the two vocabularies visible on any leaf. Ontology methods are PascalCase — ExecuteRaw, Delete, IsActive, Reset — while Entity’s own general infrastructure remains camelCase — addTag, getRID, getArena, getSourceModule. A reader of any leaf, or of any work function, can tell at a glance which calls are ontology surface and which are substrate machinery, without consulting a header.

A.2 A Minimal, Terminal Constraint: Deletable

The interface is one method:

class Deletable_ : virtual public ETCS::Entity {
public:
    virtual ~Deletable_() = default;
    virtual bool Delete() = 0;
};

Its base is correspondingly minimal — an instance hook and one dispatch pair:

ETCS_SUPERTYPE_BASE(Deletable) {
    ETCS_MAKE_INSTANCE(Deletable)
    ETCS_DISPATCH_METHOD(bool, Delete);
};

A leaf inheriting DeletableBase<Leaf> owes exactly one obligation, DeleteConcrete(). Deletable is a leaf-level example of a constraint stable enough to treat as fixed: its meaning — this entity can be asked to destroy itself — is complete, and no refinement of it is anticipated.

A.3 A Lineage That Refines by Position, Not by Method: Database → LocalDatabase

Database_ declares the shared database constraint (connection lifecycle, schema, raw execution) and additionally carries real non-virtual behavior in the interface itself: transaction bracketing on an atomic flag, a compare-and-swap BeginTransaction / Commit / Rollback trio, and an RAII TransactionGuard. None of these is a dispatch method, so none is an obligation a leaf must discharge — and a module may still choose to expose them as actions, which the shipped provider does. That is the surface independence of Section 2.8 seen from its less obvious side: a module exporting behavior that no family’s contract required it to export, rather than declining to export behavior that one did. LocalDatabase_ refines the family by publicly inheriting Database_ and adding no new obligations whatsoever:

class LocalDatabase_ : public Database_ {
public:
    LocalDatabase_() {}
    virtual ~LocalDatabase_() = default;
};

This is not a placeholder awaiting content. Database_ is a structural intermediate and publishes no base, so no leaf claims it; what a leaf claims is LocalDatabase or its sibling RemoteDatabase, each of which carries a base and each of which declares nothing beyond the shared constraint. The two therefore present the same method surface and hold different hash identities, which is precisely the case Section 2.3 states in the abstract, here realized in the shipped ontology. The refinement is positional: claiming this node asserts that the realization stores locally, constraining which leaves may legitimately occupy it rather than what methods they must write. Identity in ETCS is owned by the type, not derived from its method surface, and this lineage is where that stops being a claim and becomes a file.

Its base illustrates the cumulative rule directly — it dispatches the entire accumulated surface walked back through Database_, not merely LocalDatabase_’s own (empty) increment:

ETCS_SUPERTYPE_BASE(LocalDatabase) {
    ETCS_MAKE_INSTANCE(LocalDatabase)
    ETCS_DISPATCH_METHOD(void, CloseConnection);
    ETCS_DISPATCH_METHOD(void, CreateConnection, (const ETCS::Buffer&, db));
    ETCS_DISPATCH_METHOD(bool, ExecuteRaw, (ETCS::Buffer&, data));
    ETCS_DISPATCH_METHOD(bool, InitializeSchema, (const ETCS::Buffer&, schema));
};

A.4 The Concrete Leaf

This lineage is likewise a settled part of the ontology: the database constraint’s shape is considered stable, with concrete leaves realizing it rather than reopening it. The concrete leaf is correspondingly light. A SQLite realization inherits the family in one line and owes only the *Concrete slots the accumulated base surface demands:

class SqliteLocalDatabase : public LocalDatabaseBase<SqliteLocalDatabase> {
public:
    WIRE_TYPE_IDENTITY(SqliteLocalDatabase);
    ~SqliteLocalDatabase() override { CloseConnectionConcrete(); }

    void CreateConnectionConcrete(const ETCS::Buffer& db_info) override {
        if (connected) return;
        dbPath = db_info;
        if (sqlite3_open(dbPath.c_str(), (sqlite3**)&db) == SQLITE_OK)
            connected = true;
    }

    bool ExecuteRawConcrete(ETCS::Buffer& data) override {
        if (!connected || !db) return false;
        return sqlite3_exec((sqlite3*)db, data.c_str(),
                            nullptr, nullptr, nullptr) == SQLITE_OK;
    }

    // CloseConnectionConcrete and InitializeSchemaConcrete similarly.
};

The leaf never names Database_ or LocalDatabase_, never touches the outer dispatchers, and never re-implements the transaction machinery — it fills in four concrete slots and inherits the entire accumulated surface, interior included. It writes no dispatch logic, no identity registration beyond one macro, and no lifecycle wiring. A complete working database binding is on the order of seventy lines because the family has already done the structural work; the leaf supplies only what is specific to SQLite.

Composition remains open at the leaf. Adding a second family is a second base in the inheritance list and its obligations discharged; folding DeletableBase<SqliteLocalDatabase> into this type costs one clause and one method, with no change to the database lineage or to any consumer of it.

The swappability is the substance of the stability claim. Because .etcs scripts address the LocalDatabase constraint surface rather than this leaf, a different realization — a Postgres leaf, an in-memory test double — is another one-line inheritance discharging the same four obligations, and every script written against LocalDatabase runs against it unmodified. The constraint is fixed while the leaf is free: this is Section 6’s monotone extensibility shown at leaf granularity, a new realization participating fully with zero consumer change.

A.5 The Interior, Concretely

The constraint-surface / interior boundary of Section 2.8 is clearest in a module that does substantial work behind a small exported surface. NetworkProvider is such a module, and its interior holds two distinct kinds of thing that no trace can name.

The first is machinery that is not an ontology type at all. LocalPipePair is a plain struct in the provider’s own header:

// Internal helper — allocates a SharedPage from the module-local arena and
// creates a Pipe pair. Used for in-module producer/consumer chains that drive
// ParseConcrete directly, not through the entity call() interface.
// Lifetime of the page is bounded to the calling function's frame.
struct LocalPipePair
{
    ETCS::MirrorBuffer  producer;
    ETCS::MirrorBuffer  consumer;
    ETCS::SharedPage*   page = nullptr;

    explicit LocalPipePair(const ETCS::SignalContext& ctx)
    {
        producer.bindContext(ctx);
        consumer.bindContext(ctx);
        page = ETCS::SharedPage::allocate(ETCS::MemoryArena::getInstance(), 0);
        ETCS::MirrorBuffer::makePair<ETCS::StrategyPipe, ETCS::SharedPage>(
            producer, consumer, page, 0, 0);
    }

    ~LocalPipePair()
    {
        ETCS::MirrorBuffer::teardownPair<ETCS::StrategyPipe, ETCS::SharedPage>(
            producer, consumer, page);
    }
    // non-copyable
};

This builds a complete MirrorBuffer pair — the same transport primitive Section 2.3.1 describes carrying streaming content across a boundary — entirely within a work function’s frame, and tears it down when the frame exits. HTTPParser::ParseRequest, ParseResponse, and ConsumeRequest each use one, as does TLSContext::ReceiveData.

Its un-nameability is structural rather than chosen, and that is the point worth taking from the example. LocalPipePair is not an Entity. It holds no tag, carries no hash identity, appears in no tag block, and therefore receives no Make, no List, and no trampoline. There is no export for a trace to address, and no way for an author to add one — exposing this to scripting would mean redesigning it as a provided type first. That is the difference between the interior and a surface that merely happens to be unexported.

The second kind is entity state whose exported surface is deliberately far smaller than the behavior it governs. SocketConnectionState exports five actions:

ETCS_TAG_BLOCK_BASIC(SocketConnectionState,
    Reset, Close, IsOpen, SetPage, GetPage
)

The connection lifecycle those five sit on runs through members appearing in no tag block: checkTimeout, markActive, NoteSubmit, NoteComplete, RecycleForNextRequest, CanKeepAlive, Served, GetClientFd, RecvBuffer, SendBuffer, GetParser. HttpServer::Serve drives all of them across a recursive submission chain — receive, parse, route, send, then either recycle for the next request on the same descriptor or drain — and every step of it is invisible to any trace. What a script may say to a connection is reset it, close it, is it open, and two page-binding calls. What the module does with a connection is the whole of the above.

Both cases make the same point from different directions, and neither is an aspiration. The implementation behind a work function is ordinary Turing-complete C++ with unbounded internal behavior — a submission chain that re-arms itself until a request completes is precisely the kind of thing exhaustion does not attempt to enumerate — while the surface a trace addresses stays finite and declared.

The same module also shows the two surfaces diverging by name, which Section 2.8 permits and this author uses. HTTPParser is a Parser_ leaf, so its constraint surface carries Parse and its leaf implements ParseConcrete. Neither name is exported. The tag block declares ParseRequest and ParseResponse as immediate actions and ConsumeRequest and ProduceResponse as streaming ones — four causal actions over one constraint obligation, each setting a parse mode and then calling ParseConcrete directly. The constraint fixes what the type is; the tag block fixes what can be said to it; and one obligation became four names because that is what a trace addressing an HTTP parser actually wants to say.

A.6 A Family That Declines to Over-Specify: Ephemeral

Ephemeral_ models a mutable, RID-addressable live object with a bounded lifetime — a connection, a session, a transaction — and declares only two obligations: Reset() and a const-qualified IsActive(). Its base is two dispatch lines, one of them the const variant.

What it deliberately does not declare is instructive, and the reason is structural rather than stylistic. Serialization and deserialization are genuine capabilities of these objects, and they are left to produce/consume work functions on the concrete leaf rather than declared as virtuals here.

The immediate reason is expressive: the produce/consume contract already carries the right shape — a MirrorBuffer with a structured-lifetime SignalContext — and a virtual method signature would express strictly less of it. The load-bearing reason is what that shape does for allocation. Serialized payloads are variable-length, and variable length is precisely what the arena’s recurring-class property (Section 4.2) requires be kept off the allocation path. Routing them through the transport primitive holds unbounded shapes in an object with an explicit lifetime contract between two locales, and leaves the module arena seeing only the recurring classes its type and struct shapes define. Declaring serialization as a virtual would have placed variable payloads on the ordinary allocation path and reintroduced exactly the non-recurring size class the substrate is arranged to avoid.

A family declares the minimum needed for the type system to reason about its members uniformly; behavior whose shape is already captured by a substrate primitive belongs to that primitive, not to a redundant virtual.

A.7 Orthogonal Composition

A concrete type composes one node from each of several independent families at once. StaticHtmlPage draws from three:

class StaticHtmlPage
    : public HtmlPageBase<StaticHtmlPage>,
      public EphemeralBase<StaticHtmlPage>,
      public DeletableBase<StaticHtmlPage> { /* ... */ };

Its obligations are the union of the three walks back to the shared Entity root: ResetConcrete and IsActiveConcrete discharge the Ephemeral walk, IsFileBackedConcrete and the content surface discharge the HtmlPage walk, DeleteConcrete discharges the Deletable walk.

Composition may also be expressed one layer earlier. A family’s own base may fold in another family’s base directly — a domain-role base composing the lifecycle base alongside its own interface — which bundles two axes that always travel together into a single pick, so that a leaf claiming the domain role acquires the lifecycle obligation without naming it. Ephemeral is in practice the axis folded this way, since nearly every domain role has bounded lifetime. The choice between folding at the base and composing at the leaf is one of whether the pairing is intrinsic to the role or incidental to this particular type; both produce the same accumulated obligation set, and neither affects the composition algebra, since exclusivity is scoped within a family and never across independent ones. None of the three collides with another — they are orthogonal axes (content, lifecycle, destructibility), composed freely at the base layer, exactly the orthogonal-family case of Section 2.1.1. FileHtmlPage composes the same three families to a different leaf, and its module tag block exports a different action set (LoadFromDisk, MountExternal, Resolve, and others) over that shared constraint surface — the two surfaces diverging precisely as Section 2.8 describes.
